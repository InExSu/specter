# Участие в разработке Specter

Specter следует методологии Spec-Driven Development. Вклад в проект подчиняется той же методологии.

## Правило

**Сначала спецификации, потом тесты, потом код.** Без исключений.

## Как внести вклад

### 1. Форк и ветка

```bash
git clone https://github.com/YOUR_USERNAME/specter.git
cd specter/specter
go build ./cmd/specter/
git checkout -b feat/your-feature
```

Цельтесь в **текущую рабочую ветку**, а не в `main`. См. [Процесс работы с ветками](#процесс-работы-с-ветками) ниже.

### 2. Напишите (или обновите) спецификацию

Каждое изменение требует спецификации. Если вы добавляете новое правило проверки, сначала напишите `specs/your-rule.spec.yaml`. Если вы меняете существующее поведение, обновите соответствующую спецификацию в `specs/`.

Используйте каноническую схему. Проверьте спецификацию:

```bash
./specter parse specs/your-rule.spec.yaml
```

### 3. Напишите тесты по AC

Каждый критерий приёмки в вашей спецификации становится тестом. Аннотируйте тесты через `@spec` и `@ac`:

```go
// @spec your-rule
package yourrule

// @ac AC-01
func TestDoesTheThing(t *testing.T) {
    // ...
}
```

### 4. Реализуйте

Теперь пишите код. Спецификация говорит, что строить. Тесты говорят, когда вы закончили.

### 5. Проверьте

```bash
make check   # go vet + go test + go build
make dogfood # specter validates its own specs
```

Всё должно проходить.

### 6. Коммитьте в стиле Conventional Commits

```
feat(check): add duplicate constraint ID detection
fix(parse): handle YAML tabs correctly
docs: update CLI reference
```

Полный формат коммитов см. в [RELEASE_PLAN.md](specter/docs/archive/RELEASE_PLAN.ru.md).

### 7. Откройте PR

- Заголовок: в формате conventional commit
- Описание: ссылка на спецификацию и перечень покрытых AC
- **Базовая ветка: текущая рабочая ветка** (см. ниже), а не `main`, если только это не хотфикс для ошибки в выпущенной версии
- Все проверки CI должны проходить

```bash
# Явно укажите текущую рабочую ветку — не полагайтесь на ветку по умолчанию.
# Активный цикл можно найти, перечислив ветки release/* на GitHub:
#   gh api repos/Hanalyx/specter/branches --jq '.[].name | select(startswith("release/"))'
gh pr create --base release/vX.Y.Z --title "..."
```

## Процесс работы с ветками

Specter использует модель **рабочей ветки выпуска**. У каждого цикла выпуска есть одна долгоживущая ветка, обычно `release/vX.Y.Z`, которая накапливает все изменения функций, исправлений и документации до момента выпуска. `main` получает одно слияние на каждый выпуск.

```
main
 │
 ├── release/vX.Y.Z  ← сюда целятся все PR, пока цикл идёт
 │    ├── feat/some-feature
 │    ├── fix/some-bug
 │    └── docs/something
 │
 └── hotfix/vA.B.C  ← хотфиксы ответвляются от main, сливаются в main, минуя рабочую ветку
```

Между выпусками `main` — единственная ветка, и PR целятся прямо в неё. Ветки только для сопровождения (например, внутренний рефакторинг `chore/dogfood-strict`, выпущенный 2026-04-24) используют имя `chore/<name>` и сливаются без повышения версии.

### Правила

1. **Все PR с функциями, исправлениями и документацией целятся в текущую рабочую ветку.** Не в `main`. Активную ветку ищите перечислением ветвей `release/*` на GitHub (например, `gh api repos/Hanalyx/specter/branches --jq '.[].name | select(startswith("release/"))'`).
2. **Рабочая ветка называется по выпуску** — `release/v0.10`, `release/v0.11` и т.д. Создаётся в начале цикла; удаляется после слияния в `main` и простановки тега выпуска.
3. **Хотфиксы — исключение.** Ошибка в выпущенной версии на `main` исправляется через `hotfix/v0.9.3` (или аналогичную ветку), ответвлённую от `main`, PR в `main`, слияние и тег. Текущая рабочая ветка позже вливает `main` вперёд, чтобы подхватить хотфикс.
4. **Теги ставятся на `main`** после слияния рабочей ветки, никогда на самой рабочей ветке. Тег = «этот коммит выпущен пользователям».
5. **`--base` указывается явно** при открытии PR. Настройка базовой ветки по умолчанию на GitHub остаётся `main`; участники передают `--base release/vX.Y.Z` (или текущее имя рабочей ветки). PR, нацеленный не туда, — единственный режим отказа, который эта дисциплина сама поймать не может.

### Зачем

Выпуски v0.9.0 / v0.9.1 / v0.9.2 каждый попадали в `main` примерно через 5 отдельных PR. Это работает, но `git log main` превращается в журнал разработки, а не в историю выпусков — каждый WIP-коммит и итерация тестов смешиваются с релизами. Проведение WIP через рабочую ветку сохраняет `main` чистым стволом выпусков, делает вопрос «что войдёт в следующий выпуск?» отвечаемым по состоянию ветки и снижает риск force-push в общей истории.

### Когда рабочей ветки нет

Между выпусками — после того как `main` получил слияние выпуска, но до создания рабочей ветки следующего цикла — PR, которые не могут ждать (хотфиксы, срочные правки документации), целятся прямо в `main`. Это единственное время, когда main принимает PR не из рабочей ветки.

## Что делает вклад хорошим

- **Новые правила проверки** — обнаружение новых классов ошибок в спецификациях (см. `internal/checker/`)
- **Улучшения схемы** — новые необязательные поля, повышающие выразительность спецификаций
- **Исправления ошибок** — с тестом, воспроизводящим ошибку
- **Документация** — особенно реальные примеры спецификаций

## Чего избегать

- Кода без спецификации
- Тестов без аннотаций `@spec`/`@ac`
- Изменений `spec-schema.json` без предварительного обсуждения или issue
- Ломающих изменений без плана миграции

## Заметки об архитектуре

- Пакеты `internal/` — **библиотеки чистых функций**: никакого ввода-вывода, CLI и побочных эффектов
- `cmd/specter/` — **тонкая обёртка CLI** (Cobra): читает файлы, вызывает внутренние пакеты, форматирует вывод
- Правила проверки живут в `internal/checker/` — добавляйте новые правила, не трогая оркестратор
- Тесты лежат рядом с исходником (`internal/parser/parse_test.go` рядом с `parse.go`)
- Тестовые фикстуры живут в `testdata/`
