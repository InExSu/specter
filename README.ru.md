# Разработка через спецификации

> *«Спецификации — не костыль для слабых моделей. Это средство защиты для мощных.»* <!-- doc-style: allow --><!-- verbatim quotation from sddbook/MODULE_01/CHAPTER_01.md -->
>
> Mastering Spec-Driven Development, глава 1

Инструменты ИИ-кодинга генерируют код быстрее, чем человек способен его проверить. Узкое место теперь не написание кода, а понимание, делает ли код именно то, что вы задумали. Промпты на естественном языке неоднозначны. ИИ молча, уверенно и зачастую неверно заполняет все пробелы. Код работает. Замысел уплыл.

**Spec-Driven Development (SDD, разработка через спецификации)** — это ответ: напишите структурированную спецификацию до того, как ИИ напишет хотя бы строку кода. Спецификация снимает неоднозначность, фиксирует ограничения и определяет, что значит «готово». ИИ становится исполнителем контракта, а не толкователем пожелания.

В этом репозитории есть две вещи, которые работают вместе:

---

## Specter: инструментарий

**Specter** проверяет, связывает и типизирует файлы `.spec.yaml` так же, как `tsc` проверяет файлы `.ts`.

Без Specter спецификация — просто документ. Со Specter спецификация становится проверяемым контрактом. Запустите его перед реализацией, чтобы поймать ошибки в спецификации, и добавьте `specter sync` в CI, чтобы блокировать сломанные спецификации или спецификации ниже порога.

```
$ specter sync
Specter Sync

  PASS parse: 15 spec(s) parsed successfully
  PASS resolve: 15 specs, 23 dependencies resolved
  PASS check: 0 warning(s), 0 info
  PASS coverage: 15 spec(s) meet coverage thresholds


All checks passed.
```

Specter не зависит от предметной области. Файл `.spec.yaml` может описывать поведение во время выполнения, инварианты данных, политику безопасности, контракты схем, архитектурные правила или любой другой контракт компонента. Подходит всё, у чего есть ограничения и критерии приёмки. Конвейер проверяет форму, а не категорию.

## Замысел человека, исполнение ИИ

Схема Specter намеренно подробна: ограничения, критерии приёмки, уровни, происхождение, пороги покрытия. Писать всё это вручную для каждого модуля было бы непрактично, и это никогда не подразумевалось.

Задуманный рабочий процесс — сотрудничество между вами и вашим ИИ-ассистентом по коду:

1. **Вы задаёте замысел:** краткое описание того, что должен делать модуль, его ключевые ограничения и любые неочевидные решения или компромиссы
2. **ИИ пишет спецификацию:** переводит ваш замысел в полностью структурированный файл `.spec.yaml` с ограничениями, AC и назначением уровней
3. **ИИ пишет тесты:** напрямую выведенные из AC в спецификации
4. **Вы проверяете:** спецификация и тесты — это шлюз одобрения; вы убеждаетесь, что ИИ правильно понял замысел, прежде чем начнётся реализация
5. **ИИ реализует:** спецификация как контракт, тесты как проверка

Specter проверяет артефакты, которые перед ним лежат, а не порядок, в котором вы их написали. Он проверяет, что каждая спецификация разбирается и связывается. Он измеряет покрытие по аннотациям `@spec` и `@ac` в ваших тестах. По умолчанию он засчитывает аннотированный критерий только тогда, когда соответствующий тест прошёл, — в результатах, которые вы загружаете через `specter ingest`. Он завершает `specter sync` с ошибкой, когда спецификация не дотягивает до порога своего уровня. Так правила становятся инфраструктурой, а не пожеланием.

**Главная задача: провести ваш ИИ-ассистент по коду через спецификацию, тест, реализацию и оценку в правильном порядке, каждый раз, сохраняя ваш замысел на всём протяжении.**

## Основной цикл

```
Write spec  ->  Validate spec  ->  Generate code  ->  Annotate tests  ->  Enforce coverage
     ↑                                                                        |
     └────────────────── Refine spec when intent drifts ────────────────────┘
```

За каждым шагом этого цикла стоит команда Specter:

| Шаг | Команда | Что проверяет |
|---|---|---|
| Проверить спецификацию | `specter parse` | Корректность схемы, обязательные поля, допустимые ID |
| Связать спецификации | `specter resolve` | Зависимости, отсутствие циклов, совместимость версий |
| Проверить структуру | `specter check` | Изолированные ограничения, структурные конфликты |
| Обеспечить покрытие | `specter coverage` | Тесты прослеживаются к AC по аннотации и, по умолчанию, по успешному прохождению; каждая спецификация достигает порога своего уровня |
| Защитить CI | `specter sync` | Всё вышеперечисленное; ненулевой код выхода при любом сбое |

## Почему структура важнее кода

Книга описывает три режима отказа, которые снова и снова появляются в разработке с помощью ИИ:

**Неоднозначность превращается в решения.** «Сделай страницу настроек» содержит десятки неотвеченных вопросов. ИИ отвечает на все них молча, опираясь на обучающие данные, а не на ваш замысел. Спецификация заставляет человека принять эти решения до того, как ИИ начнёт.

**Код расходится с замыслом.** Тесты проходят. Функция выпускается. Но ИИ использовал шаблон, который вы не хотели, пропустил важное для вас ограничение или выполнил букву требования, нарушив его дух. Без спецификации не с чем сравнивать, чтобы заметить расхождение. Со спецификацией и Specter расхождение обнаружимо.

**Знание испаряется между сессиями.** Каждая новая сессия ИИ начинается с нуля. Ограничения, которые вы выстрадали в прошлом спринте, архитектурные решения, принятые месяц назад, — всё исчезло. Файл спецификации — это постоянная память, которая путешествует вместе с кодом и может быть внедрена в любую сессию ИИ как контракт.

## Быстрый старт

```bash
# Установить Specter
OS=$(uname -s | tr '[:upper:]' '[:lower:]')
ARCH=$(uname -m); case "$ARCH" in x86_64) ARCH=amd64 ;; aarch64) ARCH=arm64 ;; esac
VERSION=$(curl -sL https://api.github.com/repos/Hanalyx/specter/releases/latest | grep '"tag_name"' | head -n1 | cut -d'"' -f4 | sed 's/^v//')
curl -LO "https://github.com/Hanalyx/specter/releases/download/v${VERSION}/specter_${VERSION}_${OS}_${ARCH}.tar.gz"
tar xzf "specter_${VERSION}_${OS}_${ARCH}.tar.gz"
sudo mv specter /usr/local/bin/

# Проверить первую спецификацию
specter parse my-feature.spec.yaml

# Загрузить результаты тестов, затем запустить весь конвейер.
# Строгий режим по умолчанию засчитывает критерий, только если его тест прошёл.
specter ingest --junit test-results.xml   # или --go-test results.json
specter sync
```

`specter ingest` засчитывает тест, только когда идентификаторы спецификации и критерия доходят до вывода раннера. Поместите токен `spec-id/AC-NN` в имя теста или класса либо печатайте строки `// @spec <id>` и `// @ac AC-NN` из тела теста. Каждому напечатанному маркеру нужен префикс комментария — `//`, `#` или `*`. Одних исходных комментариев `// @spec` и `// @ac` недостаточно.
