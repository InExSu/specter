# Релизы Specter

Этот документ определяет шлюз, который должен быть пройден перед любым `vsce publish` (расширение VS Code) или `git push origin vX.Y.Z` (релиз CLI).

Он существует из-за релизов расширения v0.8.0–v0.8.3. За один день вышло четыре патч-релиза, каждый исправлял баг, который первый реальный пользователь находил при установке. Они доказали, что запуска `make check` и `vsce package` недостаточно для поставки. Marketplace — канал распространения, а не тестовый стенд.

---

## Шлюз

Каждый шаг обязателен.

### 1. CI зелёный

Каждая задача в `ci.yml` проходит в GitHub Actions. Обязательно, но само по себе недостаточно.

### 2. Установите упакованный VSIX локально

```bash
code --install-extension specter-vscode-X.Y.Z.vsix --force
```

Зелёный прогон тестов — не то же самое, что VS Code, загружающий пакет. В VSIX v0.6.5 попал устаревший каталог `out/`, исправлено в v0.6.6 (коммит 0c28155); см. GOTCHAS #1 и #2.

### 3. Перезагрузите, затем откройте заведомо рабочее тестовое пространство

Сам репозиторий `specter/` — хороший выбор. Боковая панель Coverage должна перечислять каждую dogfood-спецификацию, а не сообщение пустого состояния.

### 4. Перезагрузите, затем откройте заведомо падающее тестовое пространство

Каталог, чьи `.spec.yaml` не проходят схему Specter (например, спецификации, написанные в старой кастомной схеме). Проверьте три вещи:

- **Боковая панель Coverage.** Она показывает сворачиваемую группу с меткой `Failed to parse: N file(s)`, с одним дочерним элементом на падающий файл. Клик по дочернему открывает этот файл. Предположим, каждая спецификация в рабочем пространстве упала с одним типом ошибки по одному и тому же пути, и таких файлов минимум два. Тогда метка добавляет `schema drift` с типом ошибки и её путём, если он есть, например `schema drift (required at spec)`. Подсказка группы также советует запустить `specter doctor`. Иначе метка — просто счётчик. Боковая панель показывает сообщение пустого состояния, только когда в рабочем пространстве нет спецификаций и нет ошибок парсинга.
- **Строка состояния.** Она читается как `Specter: error` на фоне ошибки. Её подсказка: «Specter: parse errors. Click to view details.»
- **Канал Output.** Он перечисляет каждую ошибку парсинга под строкой с их подсчётом, по одной строке на ошибку с файлом и сообщением.

Группа боковой панели — в `vscode-extension/src/coverage.ts`. Строка состояния и строки канала Output — в `vscode-extension/src/extension.ts`, где прогон покрытия обрабатывает ошибки парсинга.

### 5. Пройдите каждый изменённый путь кода

Если изменение затрагивает:
- **Разрешение бинарника**: выполните **Specter: Re-download CLI** и наблюдайте загрузку в `~/.specter/cli/`. Удаление приватной копии само по себе не всегда запускает загрузку, потому что расширение сначала использует CLI в диапазоне из `specter.binaryPath`, PATH или `~/.specter/bin/specter`.
- **Отрисовку дерева**: проверьте и пустое, и заполненное состояние.
- **Обработку флагов CLI**: вызовите затронутую команду из встроенного терминала.
- **Поток активации**: откройте рабочее пространство, подходящее под триггер активации, но не открытое при запуске VS Code.

Если изменение явно не проходит через один из этих путей, запишите путь, который оно реально задействует, и проверьте его явно.

### 6. Проверьте канал Output

Откройте панель Output из меню View и выберите Specter в её выпадающем списке, или выполните **Specter: Show Output Log**. Ожидается отсутствие необъяснённых красных записей при обычной работе.

### 7. Человек проверяет и одобряет

Человек воспроизводит изменение в живом окне VS Code и подтверждает, что оно соответствует замыслу. Отчёт тестов или заявление агента этот шаг не удовлетворяют. Во время релизов v0.8.x этого шага не было — поэтому шлюз и существует.

### 8. Только теперь запускайте `vsce publish`

Для нетривиальных изменений (сдвиги схемы, новые поверхности UI, код загрузки бинарника, новые флаги CLI) сначала публикуйте как `--pre-release`. Держите релиз в канале предрелизов достаточно долго, чтобы проблемы всплыли, прежде чем переводить его в стабильный.

Стабильные публикации зарезервированы для небольших патчей с низким риском.

```bash
# Non-trivial: prefer pre-release first
npx vsce publish --packagePath specter-vscode-X.Y.Z.vsix --pre-release

# Small low-risk patch (after pre-release has baked, or for trivial fixes)
npx vsce publish --packagePath specter-vscode-X.Y.Z.vsix
```

## Теги релиза CLI

Запушенный тег запускает релиз CLI. На теге запускается Pre-Release Test Suite, а `release.yml` собирает и подписывает только после разрешения read-only шлюзовой задачи. Шлюз живёт в `.github/scripts/release-gate.sh`. Он разрешает релиз, только когда выполнены все условия:

- Тег — аннотированный тег с именем `vX.Y.Z` или `vX.Y.Z-suffix` для предрелиза. Создавайте подписанный аннотированный тег через `git tag -s vX.Y.Z -m "vX.Y.Z"`. Если ключ подписи не настроен, шлюзу удовлетворяет и `git tag -a`. Шлюз не проверяет подписи.
- Тег указывает на коммит в `main`.
- `specter/VERSION` на этом коммите совпадает с тегом без `v`.
- Pre-Release Test Suite прошёл при пуше этого тега, на этом коммите.

Ручной запуск `release.yml` должен выполняться из `main` и проходит через тот же шлюз.

### Защита тегов

Два ruleset репозитория покрывают `refs/tags/v*`:

- **Release tags: creation by the release operator only.** Только оператор релиза может создать тег `v*`.
- **Release tags: immutable.** Никто не может переместить или удалить тег `v*`. У этого ruleset нет обхода.

Релиз GitHub привязан к имени тега, а не к собранному коммиту. Тег, перемещённый во время релиза, оставил бы страницу релиза указывающей на другой коммит, чем бинарники. Именно это предотвращает immutable ruleset.

### Восстановление релизного тега

Перемещение или удаление релизного тега — шаг восстановления, а не рутинная работа. Делайте это, только когда тег был запушен на неверный коммит и из него не опубликован релиз.

1. Зафиксируйте причину в issue, с тегом, неверным коммитом и правильным.
2. В Settings, Rules, Rulesets переведите **Release tags: immutable** в Disabled.
3. Удалите или переместите тег и запушьте исправленный тег.
4. Верните ruleset в Active. Убедитесь через `gh api repos/Hanalyx/specter/rulesets`, что оба ruleset читаются как `active`.

История ruleset фиксирует, кто и когда отключил и снова включил его. Не перемещайте тег, у которого уже есть опубликованный релиз. Выпустите новую патч-версию.

### Инструменты сборки релиза

`release.yml` и `release-snapshot.yml` устанавливают GoReleaser и syft через `.github/scripts/install-release-tools.sh`. Он скачивает каждый архив с фиксированного релизного URL и проверяет его по закреплённому SHA-256 перед извлечением. Чтобы обновить инструмент:

1. Скачайте файл контрольных сумм нового релиза и его подпись.
2. Проверьте подпись через `cosign verify-blob` по идентичности собственного release workflow инструмента. Заголовок скрипта называет каждую идентичность.
3. Одним изменением обновите скрипт: версию, хеш архива из проверенного файла контрольных сумм и идентичность в заголовке. Идентичность GoReleaser называет его релизный тег, поэтому меняется с каждой версией. Проверяйте с `--certificate-oidc-issuer https://token.actions.githubusercontent.com`.
4. Откройте изменение как pull request. Предполётная проверка snapshot запускается на любое изменение в `.github/scripts/`, поэтому неверный хеш упадёт там, а не на релизном теге.

## Помощник

`make release-check` автоматизирует первую половину шлюза. Он запускает `make prerelease`: `make check`, тесты с детектором гонок, govulncheck, dogfood, кросс-компиляцию, а также typecheck, lint, тесты и упаковку VSIX расширения. Затем печатает чек-лист шагов 2–8, пронумерованных 1–7. Он **не** запускает `vsce publish` ни при каких обстоятельствах. Это остаётся ручным, чтобы вы не могли пропустить проверку.

```bash
make release-check
# ... prints the checklist, then exits. You then perform gate steps 2 to 7 by hand
#     before running vsce publish.
```
