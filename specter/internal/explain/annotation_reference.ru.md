# Справочник по аннотациям тестов

Как аннотировать тесты, чтобы `specter coverage` их считал, а `specter coverage --strict` проверял.

Это аналог `SPEC_SCHEMA_REFERENCE.md`. Справочник по спецификациям определяет схему для файлов `.spec.yaml`. Этот справочник определяет схему для аннотаций тестов.

---

## Что читает Specter

Specter читает аннотации из двух мест. Они служат разным целям, и оба существуют не просто так.

| Канал | Источник | Читает | Назначение |
|---|---|---|---|
| 1 | Комментарии `// @spec <id>` и `// @ac AC-NN` над тестовой функцией | `specter coverage` | Считает, у каких AC есть аннотированные тесты. |
| 2 | `<spec-id>/AC-NN` в выводе теста, видимом раннеру (заголовок теста или лог выполнения) | `specter ingest` | Записывает pass/fail по каждому AC в `.specter-results.json`. Требуется для `specter coverage --strict`. |

**Пишите оба.** Тест только с каналом 1 считается, но не проверяется. Под `--strict` «считается, но не проверяется» равно «не покрыт», и AC понижается.

## Правила

1. **Формат комментария к исходнику.** Над каждой тестовой функцией:
   ```
   // @spec <spec-id>
   // @ac AC-NN
   ```
   Один `// @spec` на тест. Один `// @ac` на каждый AC, который покрывает тест. Языки, отличные от C-семейства, используют свой символ комментария: `#` для Python, `--` для SQL и т.д.

2. **Формат, видимый раннеру.** Пара `(spec-id, AC-NN)` появляется в одном из мест:
   - Заголовок теста: `<spec-id>/AC-NN` или `<spec-id>:AC-NN` где-то в имени.
   - Тело теста, напечатанное во время выполнения: `// @spec <spec-id>` и `// @ac AC-NN` на отдельных строках.

3. **Формат spec id.** Нижний регистр, kebab-case. Соответствует регулярному выражению `[a-z][a-z0-9-]*[a-z0-9]`. Начинается с буквы. Заканчивается буквой или цифрой. Без подчёркиваний, без верхнего регистра, без ведущего или хвостового дефиса.

4. **Формат AC id.** Минимум две цифры с дополнением нулями: `AC-01`, `AC-02`, `AC-12`, `AC-100`. **`AC-1` не соответствует `AC-01`.** Регулярное выражение принимает `AC-\d+`, поэтому однозначные формы извлекаются как `AC-1`. Но шлюз покрытия сравнивает по строковому равенству со спецификацией, а спецификация использует `AC-01`.

5. **Один AC на тест.** Каждая тестовая функция или подтест покрывает ровно одну пару `(spec-id, AC-NN)`. Запись JUnit `<testcase>` или событие теста `go test -json` несёт один заголовок, поэтому `specter ingest` назначает одну пару на запись. Тест с несколькими AC теряет AC под `--strict`.

6. **Одно соглашение на файл.** Ingest принимает обе формы. Смешивать их в одном файле законно, но чревато ошибками при миграции. Выберите одну форму на файл.

7. **Регулярное выражение извлечения** (из `specter/internal/ingest/annotations.go`):
   ```
   ([a-z][a-z0-9-]*[a-z0-9])[/:](AC-\d+)
   ```
   Разделитель между spec id и AC id — `/` или `:`. Ничего другого. `_`, `-`, `.` и пробелы не работают.

## По раннерам и языкам

### Go (`go test -json`)

Используйте `t.Run`, чтобы у каждого AC был собственный подтест и собственная запись, видимая раннеру.

```go
// @spec user-create
// @ac AC-01
// @ac AC-02
func TestCreateUser(t *testing.T) {
    t.Run("user-create/AC-01 valid credentials returns 201", func(t *testing.T) {
        // assertions
    })
    t.Run("user-create/AC-02 invalid email returns 400", func(t *testing.T) {
        // assertions
    })
}
```

`go test -json` испускает события с `Test: "TestCreateUser/user-create/AC-01 valid credentials returns 201"`. Регулярное выражение находит `user-create/AC-01`.

### TypeScript / Jest / Vitest (репортер JUnit)

Поместите пару в каждый заголовок `it` или `test`.

```typescript
// @spec user-create
// @ac AC-01
test('[user-create/AC-01] valid email and password creates user and returns 201 with JWT', () => {
    // assertions
});

// @spec user-create
// @ac AC-02
test('[user-create/AC-02] invalid email format returns 400', () => {
    // assertions
});
```

Запуск с выводом JUnit:
- Jest: `jest --reporters=jest-junit`
- Vitest: `vitest run --reporter=junit --outputFile=test-results.xml`

JUnit `<testcase name="...">` несёт полный заголовок. Регулярное выражение находит пару внутри скобок.

### Python / pytest (известное ограничение)

Имена функций Python не могут содержать `/` или `:`. Соглашение A (по заголовку) по умолчанию не работает для pytest. **Для Python используйте соглашение B (лог выполнения).**

```python
# @spec user-create
# @ac AC-01
def test_valid_registration_returns_201(client):
    print('// @spec user-create')
    print('// @ac AC-01')
    response = client.post('/users', json={...})
    assert response.status_code == 201
```

Запуск pytest с выводом JUnit:
```
pytest --junitxml=test-results.xml -o junit_logging=all -o junit_log_passing_tests=True
```

`-o junit_logging=all` захватывает вывод `print()` в `<system-out>` для каждого тест-кейса. `specter ingest` читает `<system-out>` и сопоставляет регулярные выражения тела `//\s*@spec\s+([a-z][a-z0-9-]*[a-z0-9])` и `//\s*@ac\s+(AC-\d+)`.

**Почему не имена функций.** `def test_user_create_AC_01_valid_returns_201` испускает заголовок JUnit `test_user_create_AC_01_valid_returns_201`. Регулярное выражение требует `/` или `:` между `user-create` и `AC-01`. `_` не подходит. Используйте соглашение B (runtime `print('// @spec ...')`) для Python.

### Rust / `cargo test`

Первоклассного варианта ingest сегодня нет. Испускайте соглашение B в stdout и разбирайте вручную.

### Форма лога раннера: соглашение B

Работает на любом языке. Используйте её, когда не можете переименовать заголовки тестов (общий контракт именования, snapshot-тесты, внешние ожидания, имена функций Python).

```typescript
test('rejects zero amount', () => {
    console.log('// @spec payment-charge');
    console.log('// @ac AC-03');
    // assertions
});
```
```go
func TestCharge_ZeroAmount(t *testing.T) {
    t.Log("// @spec payment-charge")
    t.Log("// @ac AC-03")
    // assertions
}
```
```python
def test_rejects_zero_amount(client):
    print('// @spec payment-charge')
    print('// @ac AC-03')
    # assertions
```

## Параметризованные тесты

Параметризованный тест создаёт одну запись JUnit на кейс. Каждый кейс несёт собственный заголовок, поэтому каждому кейсу нужна собственная пара `(spec-id, AC-NN)`.

### Vitest `test.each`

```typescript
// @spec payment-charge
// @ac AC-04
test.each([
    { amount: 0,  ac: 'AC-04', desc: 'rejects zero' },
    { amount: -1, ac: 'AC-04', desc: 'rejects negative' },
])('[payment-charge/$ac] $desc', ({ amount }) => {
    // assertions
});
```

Каждый кейс испускает заголовок вроде `[payment-charge/AC-04] rejects zero`. Регулярное выражение находит.

### pytest `@pytest.mark.parametrize`

Используйте соглашение B внутри тела теста. Заголовки — это имена функций с суффиксами параметров, которые опять же не содержат `/` или `:`.

```python
# @spec payment-charge
# @ac AC-04
@pytest.mark.parametrize('amount', [0, -1])
def test_rejects_invalid_amount(amount):
    print('// @spec payment-charge')
    print('// @ac AC-04')
    # assertions
```

### Табличные тесты Go

```go
// @spec payment-charge
// @ac AC-04
func TestReject(t *testing.T) {
    cases := []struct{ name string; amount int }{
        {"payment-charge/AC-04 zero",     0},
        {"payment-charge/AC-04 negative", -1},
    }
    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            // assertions
        })
    }
}
```

Оба подтеста испускают одну и ту же `(spec-id, AC-NN)`. `specter ingest` объединяет по худшему статусу (errored > failed > skipped > passed), поэтому один падающий кейс понижает AC.

## Миграция с подхода «только исходники» в стиле v0.9

v0.9 и раньше учили аннотациям только в исходниках: `// @spec` / `// @ac` над функцией, без формы, видимой раннеру. Такие тесты работают с `specter coverage` (подсчёт аннотаций), но понижаются под `--strict` (нет записи в результатах).

### Рецепт миграции

1. **Добавьте `--reporter=junit`** (или `go test -json`) в команду тестов CI. Вывод репортера аддитивен; сохраните существующие репортеры.
2. **Переименуйте заголовки тестов** файл за файлом. В каждом файле добавьте `<spec-id>/AC-NN` в каждый заголовок теста. Комментарии к исходнику сохраните.
3. **Подключите ingest + strict**:
   ```
   specter ingest --junit 'test-results/*.xml'
   specter coverage --strict
   ```
4. **Используйте `--scope <domain>` для поэтапного внедрения.** Применяйте `--strict` к одному домену за раз. Спецификации вне выбранного домена сохраняют поведение подсчёта аннотаций v0.9. См. `CLI_REFERENCE.md` → `specter coverage` → `--scope`.

### Дисциплина «файл целиком»

Мигрируйте файлы целиком. Полумигрированный файл (часть тестов переименована, часть нет) под `--strict` понизит непереименованные тесты, даже если переименованные проходят. `--tests <glob>` ограничивает по пути; он не может ограничить по форме заголовка теста внутри файла.

## Частые ошибки

**`AC-1` вместо `AC-01`.** Регулярное выражение принимает однозначные; шлюз покрытия сравнивает со спецификацией, где `AC-01`. Всегда дополняйте нулями.

**`_` между spec id и AC id.** На это натыкаются пользователи Python. `_` нет в регулярном выражении. Используйте соглашение B.

**Подчёркивание в spec id.** Spec id — kebab-case. `user_create/AC-01` не совпадает; `user-create/AC-01` совпадает.

**Верхний регистр в spec id.** `User-create/AC-01` не совпадает. Spec id соответствует `[a-z][a-z0-9-]*[a-z0-9]`.

**Два AC в одном тесте.** Под `--strict` `specter ingest` назначает одну пару на запись раннера. `test('[spec-foo/AC-01 AC-02] two things', ...)` захватывает только `spec-foo/AC-01`. Разделите на два теста.

**Аннотации только в исходнике в мигрированном файле.** `specter coverage` их посчитает; `specter ingest` выбросит их из результатов; `specter coverage --strict` их понизит. Проверяйте строку сводки `ingest` (`Scanned N; extracted M; dropped K`). K должен быть нулём для полностью мигрированных файлов.

**Смешение соглашений A и B в одном файле.** Ingest обрабатывает оба, но смесь — запашок миграции. Выберите одно.

**Репортер не подключён.** `ingest --junit` против несуществующего файла — жёсткая ошибка. `--junit 'test-results/*.xml'` против пустого glob даёт ноль записей; `--strict` тогда понижает всё и выдаёт предупреждение о пустых результатах.

## Подавление `unreachable_annotation` для файла

Добавлено в v0.13.0.

`specter check --test` запускает языково-зависимый сканер достижимости, который
ловит объявления `@ac` в комментариях к исходнику, чей охватывающий тест не даёт
токена, видимого раннеру. Имя диагностики — `unreachable_annotation`
(и `unreachable_annotation_unknown`, когда форма теста нестандартная).

**Подавить для всего файла** можно, поместив маркер в любое место
файла (обычно в начало):

| Семейство языков | Строка маркера |
|---|---|
| Go, TypeScript, JavaScript, Rust | `// @reachable manual` |
| Python, shell, YAML | `# @reachable manual` |

Маркер действует на уровне файла. Одно объявление в любом месте файла
исключает каждый `@ac` в этом файле из ОБЕИХ `unreachable_annotation` и
`unreachable_annotation_unknown`, независимо от настроек манифеста.

**Когда использовать маркер:**

- Раннер тестов нестандартный (не `testing` из Go, не Jest/Vitest, не
  pytest), и сканер не распознаёт форму теста.
- Тесты генерируются динамически, и `@ac` находится на генераторе,
  а не на распознаваемой тестовой функции.
- Оператор вручную проверил, что тест действительно покрывает
  аннотированные AC через какой-то внешний канал.

**Не используйте его как глушитель шума.** Если диагностика срабатывает, потому что
в реальном заголовке подтеста Go отсутствует токен `<spec-id>/AC-NN`, исправьте
заголовок подтеста. Маркер отключает реальный сигнал. То же касается
заголовков TypeScript `describe`/`it` и строк pytest `print()`.

**Серьёзность** (когда маркера нет):

- С блоком `settings.annotation` в `specter.yaml` `unreachable_annotation` —
  это `warning`, и `check --test` выходит с 0. Значение `permissive` блока
  не меняет эту диагностику.
- `check --test --strict` или `settings.strict: true` повышают
  `warning` до `error`, и `check` выходит с ненулевым кодом. Он не может повысить
  диагностику, подавленную манифестом.
- Манифест без блока `settings.annotation` откатывается к старому ключу строгости,
  который SSRB-104 объявляет устаревшим, а v1.0.0 удаляет. Его значение по умолчанию
  тоже даёт `warning`. Его значение `annotation` подавляет диагностику
  даже под `--strict`, а значение `zero-tolerance` делает её `error`
  без `--strict`.

`unreachable_annotation_unknown` всегда `warning`, и `--strict` не
повышает её. Сканер не может сказать, действительно ли тест покрывает
AC, — только что ни один языково-зависимый парсер не распознал форму.

Пример (тест Go с кастомным помощником, скрывающим подтест от
распознавания go/ast):

```go
// @reachable manual
package foo

import "testing"

// @spec my-spec
// @ac AC-01
func TestThing(t *testing.T) {
    runWithCustomHelper(t, "my-spec/AC-01")
}
```

Без маркера `check --test` выдал бы
`unreachable_annotation_unknown`, потому что `go/ast` не может развернуть
`runWithCustomHelper`, чтобы увидеть, несёт ли заголовок теста
`my-spec/AC-01`. Маркер утверждает, что оператор проверил, что несёт.

## Устранение неполадок

**Симптом**: `specter ingest` сообщает `Scanned N; extracted 0; dropped N`.
**Причина**: заголовки тестов не соответствуют регулярному выражению. Обычно отсутствует `/` или `:`, либо вовсе отсутствует spec id.
**Проверка**: `specter ingest --junit <path> --verbose` перечисляет каждое отброшенное имя теста. Ищите ожидаемый паттерн.

**Симптом**: `specter coverage --strict` понижает каждый аннотированный AC.
**Причина**: в `.specter-results.json` ноль записей, или ни одна запись не соответствует аннотированной `(spec-id, AC-NN)`.
**Проверка**: предупреждение о пустых результатах срабатывает до отчёта о понижении. Прочитайте `.specter-results.json`; там должна быть одна запись на каждый покрытый AC.

**Симптом**: номер AC в заголовке теста — `AC-1`, в спецификации `AC-01`, и `--strict` понижает.
**Причина**: несовпадение строкового равенства. Дополните заголовок нулями.

**Симптом**: тесты pytest не дают записей аннотаций.
**Причина**: pytest по умолчанию не захватывает вывод `print()` в JUnit XML.
**Исправление**: `pytest --junitxml=out.xml -o junit_logging=all -o junit_log_passing_tests=True`.

**Симптом**: `specter check --test` выдаёт `unreachable_annotation` для теста, который, по вашему мнению, покрывает AC.
**Причина**: заголовок или тело теста не несут токен `<spec-id>/AC-NN` в форме, которую распознаёт сканер (соглашение A в заголовке подтеста или соглашение B как runtime print). Сканер сообщает, что исходный `@ac` недостижим, потому что `specter ingest` не извлёк бы соответствующую пару из вывода раннера этого теста.
**Исправление**: добавьте токен spec-id/AC-NN в заголовок подтеста (соглашение A) или напечатайте `// @spec <id>` / `// @ac AC-NN` из тела теста (соглашение B). Если тест законно покрывает AC через канал, невидимый сканеру, используйте `// @reachable manual` (или `# @reachable manual` для Python) в начале файла. Описано в разделе «Подавление `unreachable_annotation` для файла» выше.

**Симптом**: `specter check --test` выдаёт `unreachable_annotation_unknown`, а не `unreachable_annotation`.
**Причина**: файл теста на языке, для которого у языково-зависимого сканера достижимости нет парсера (всё, кроме Go, TypeScript / Jest / Vitest или Python), ИЛИ форма теста (кастомные помощники, табличные тесты с нелитеральными именами, динамически генерируемые тесты) структурно не распознана.
**Исправление**: `_unknown` всегда `warning`, при любой настройке манифеста и под `--strict`, поэтому она не валит ни один шлюз. Если вы вручную проверили, что тест покрывает AC, добавьте `// @reachable manual` в начало файла, чтобы заглушить и `_unknown`, и диагностику `unreachable_annotation` для этого файла.
