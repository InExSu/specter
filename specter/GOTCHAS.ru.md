# ПОДВОДНЫЕ КАМНИ

Неочевидные ловушки, которые уже кусали эту кодовую базу. Прочитайте перед релизом.

---

## 1. `vsce package` НЕ компилирует TypeScript

**Симптом:** в VSIX попадает устаревший `out/*.js` от прошлой сборки. `package.json` внутри VSIX сообщает новую версию, но работающее расширение исполняет старый код.

**Как это нас укусило:** выпустили VSIX v0.6.5, содержащий скомпилированный JS эпохи v0.5.x. Код исправления был в `src/`, сборка никогда не запускалась, `out/` был от предыдущего дня. Каждая установка пользователя заново запускала старый сломанный автозагрузчик, который записывал 9-байтовую строку `Not Found` (тело ответа 404) в `~/.specter/bin/specter` и делал её +x.

**Что теперь есть:**
- Хук `vscode:prepublish` в `vscode-extension/package.json`; `vsce` запускает его автоматически перед упаковкой и провалит пакет, если сборка упадёт.
- Скрипт `package` — это `npm run build && npx @vscode/vsce package` для дополнительной защиты.

**Если упаковываете вручную:** всегда сначала запускайте `npm run build` и проверяйте, что mtime `out/extension.js` новее любого файла `src/*.ts`. Быстрая проверка:
```bash
# Should return nothing (no source newer than compiled output)
find src -name '*.ts' -newer out/extension.js
```

## 2. `jest` компилирует TypeScript на лету (он НЕ пишет в `out/`)

**Симптом:** тесты проходят, вы считаете, что сборка в порядке, выпускаете сломанный VSIX.

**Как это нас укусило:** тот же инцидент, что в №1. `jest` использует `ts-jest`, который трансформирует в памяти. Проходящие тесты доказывают, что исходник корректен, но ничего не говорят о том, что лежит на диске в `out/`.

**Правило:** тесты проходят ≠ сборка актуальна. Перед любым этапом упаковки явно запускайте `npm run build`.

## 3. Node `https.get` НЕ следует редиректам и не проверяет статус

**Симптом:** загрузка тихо «успешна», но байты — это тело HTTP-ошибки (`Not Found`, HTML-страница ошибки и т.п.).

**Как это нас укусило:** код загрузки до v0.6.0 вызывал `https.get(url, ...)` и писал тело прямо на диск. GitHub Releases возвращает:
- 302-редирект на `release-assets.githubusercontent.com/...` (реальный ассет); тело 302 пустое, поэтому это тихо ломается
- 404 с телом `content-type: text/plain` `Not Found`, если URL неверен (например, `vlatest/specter_latest_...`, когда конфиг по умолчанию содержит буквальную строку `"latest"`)

**Правило:** любой `https.get` к GitHub (или любому CDN) ОБЯЗАН следовать редиректам и проверять статус. См. `vscode-extension/src/binaryDiscovery.ts:httpsGet` — правильный шаблон: до 5 редиректов, отказ при статусе >= 400, таймаут 30 с.

## 4. `cfg.get('version', 'latest')` даёт буквальную строку `"latest"`

**Симптом:** URL вроде `.../releases/download/vlatest/specter_latest_linux_amd64.tar.gz` — невалидны.

**Как это нас укусило:** код до v0.6.0 подставлял значение конфигурации прямо в URL. `"latest"` — это соглашение-ключевое слово, а не реальный тег.

**Правило:** разрешайте `"latest"` в реальный semver через GitHub API до построения URL загрузки. См. `resolveLatestVersion()` в `binaryDiscovery.ts`.

## 5. Простой `go build` внутри пакета кладёт бинарник в корень репозитория

**Симптом:** рядом с `go.mod` появляется посторонний бинарник `./specter`. Выглядит идентично `./bin/specter`, но устарел.

**Как это нас укусило:** кто-то запустил `go build` в `specter/` (без флага `-o`). Go назвал вывод по имени каталога пакета: `./specter`. Его закоммитили. Когда существовали и `./specter`, и `./bin/specter`, запуск одного вместо другого давал разные результаты: старый не имел логики исключения gap, новый имел. Потребовалась нетривиальная отладка, чтобы заметить, что это разные бинарники.

**Что теперь есть:** `/specter` в `.gitignore`. Канонический путь сборки — `make build`, который пишет `bin/specter`.

**Правило:** не запускайте простой `go build`. Используйте `make build` или `go build -o bin/specter ./cmd/specter/`.

## 6. Дублирующиеся файлы рискуют тихим дрейфом

**Симптом:** два одинаково выглядящих файла в разных путях, реально используется только один, другой медленно дрейфует.

**Как это нас укусило:** `internal/schema/spec-schema.json` и `internal/parser/spec-schema.json` существовали рядом. Загружался только парсерный (через `//go:embed`). Схемный был заброшенной копией. Они разошлись (в версии парсера было поле `coverage_threshold`, которого не было в схемной).

**Что теперь есть:** осиротевший дубликат в `internal/schema/` удалён. Каноническая схема — `internal/parser/spec-schema.json`.

**Правило:** одна каноническая копия. Если находите файл, похожий на зеркало, проверьте, какой реально загружается (grep по `//go:embed`, инструкции импорта), и удалите мёртвый.

## 7. Необязательность `specter.yaml` означает тихие значения по умолчанию

**Симптом (исправлен):** здесь описывалось, что обнаружение откатывается к `specs/` и
ничего об этом не сообщает. Ни одна половина больше не верна, и обе были проверены
по бинарнику перед переписыванием этой записи.

**Что происходит теперь.** Без `specter.yaml` обнаружение рекурсивное: спецификация в
`src/specs/spec-x.spec.yaml` находится и парсится. А когда ничего не найдено, прогон сообщает, почему искал именно там:

Он называет, где искал и что искал, затем перечисляет три
средства: сгенерировать черновики через `specter reverse`, создать каркас из шаблона через
`specter init --template` или указать другое место, добавив `specs_dir` в
`specter.yaml`. Буквальный блок здесь не воспроизводится; более ранняя ревизия
этой записи цитировала его и незаметно изменила символ маркера — тот же
дрейф, о котором предупреждает этот файл.

**Правило, которое остаётся:** если вы правите код загрузки манифеста, сохраняйте
подсказку, когда действуют значения по умолчанию. Обнаружение, сообщающее о нуле файлов, должно говорить,
где искало, — именно поэтому это больше не подводный камень.

## 8. VS Code НЕ перезагружает код расширения при обновлении или переустановке

**Симптом:** пользователь обновляет расширение, видит новый номер версии в панели Marketplace, но получает старое поведение. Строка состояния показывает что-то из старого кода.

**Причина:** хост расширений VS Code продолжает работать. Обновление расширения размещает новые файлы на диске; живой процесс продолжает исполнять старый код до перезагрузки окна. Удаление + переустановка имеет ту же проблему, если VS Code не предложит «Reload to finish».

**Правило:** отлаживая «дошло ли моё исправление?», всегда просите пользователя выполнить Developer: Reload Window, прежде чем делать вывод, что не дошло. Если публикуете критичные исправления расширения, рассмотрите повышение триггера major-activation-event или попросите пользователей перезагрузить в примечаниях к релизу.

## 9. Триггер CI `pull_request` НЕ срабатывает при правке заголовка

**Симптом:** вы правите заголовок PR (например, чтобы пройти проверку conventional-commit), затем перезапускаете упавшие задачи — они всё ещё видят старый заголовок.

**Причина:** типы по умолчанию для триггера `pull_request` — `opened, synchronize, reopened`. `edited` НЕ включён. Перезапуски используют исходный payload события.

**Обход:** запушьте пустой коммит (`git commit --allow-empty -m "ci: retrigger"`), чтобы вызвать событие `synchronize`. Или добавьте `types: [opened, synchronize, reopened, edited]` в триггер workflow.

## 10. Переменные окружения в отдельном терминале НЕ доходят до Bash-инструмента Claude Code

**Симптом:** вы делаете `export VSCE_PAT=...` в одном терминале, просите Claude Code опубликовать — оболочка Claude сообщает, что VSCE_PAT не задан.

**Причина:** у каждого терминала своё окружение оболочки. Bash-инструмент Claude Code запускает неинтерактивный подпроцесс bash, который наследует окружение от родителя Claude Code, а не от другого терминала. Экспорт в `.bash_profile` тоже не помогает: неинтерактивные оболочки его не читают.

**Как связать:**
- Напишите `! export VAR=value` как сообщение Claude (префикс `!` отправляет это в собственную оболочку Claude), ИЛИ
- Поместите экспорт в `.bashrc` (неинтерактивные оболочки читают его в некоторых дистрибутивах), ИЛИ
- Попросите Claude явно выполнить `source ~/.bash_profile` внутри вызова Bash.

## 11. AC с `gap: true` молча исключались из покрытия (до v0.6.5)

**Симптом:** обратно скомпилированная спецификация с 5 gap-AC и нулём тестов показывала статус `100%` PASS.

**Причина:** знаменатель покрытия полностью исключал gap-AC. У спецификации со 100% пробелов было `totalACs == 0`, что трактовалось как «освобождена от порога».

**Что теперь есть:** v0.6.5+ считает каждый объявленный AC, включая пробелы. Gap-AC без аннотации теста считается непокрытым. Это закреплено в C-09/AC-09 спецификации `spec-coverage`.

**Правило:** `gap: true` — маркер триажа для человеческого ревью. Он не даёт пропуск.

## 12. `constraint.enforcement` / `constraint.type` парсились, но не использовались (до v0.6.5)

**Симптом:** автор ставит `enforcement: error` на ограничение спецификации tier 3, ожидая, что оно станет ошибкой, — остаётся info.

**Причина:** проверяльщик использовал захардкоженный `orphanSeverityByTier`. Собственное поле `enforcement` ограничения игнорировалось.

**Что теперь есть:** v0.6.5+ позволяет `constraint.enforcement` переопределять значение tier по умолчанию. `constraint.type` показывается в выводе check inline. `trust_level` (парсился, но бесполезен) удалён.

**Правило:** прежде чем добавлять новое поле в схему, решите, какая часть конвейера его потребляет. Если никакая — не добавляйте или явно помечайте «только документация, не применяется».

## 13. `process.arch` ≠ `runner.arch` (регистр важен)

**Симптом:** расширение VS Code скачивает URL `.../specter_0.6.6_linux_x64.tar.gz`, который отдаёт 404. Реально опубликованный ассет — `..._linux_amd64.tar.gz`.

**Причина:** в расширении была одна функция `normaliseArch`, обслуживающая двух вызывающих с разными соглашениями о регистре:
- `runner.arch` VS Code (контекст GitHub Actions) использует верхний регистр: `X64`, `ARM64`, `IA32`.
- `process.arch` Node (то, что реально передаёт хост расширений) использует нижний: `x64`, `arm64`, `ia32`.

Switch был чувствителен к регистру и содержал только варианты в верхнем регистре. Значения в нижнем проваливались в default (`return arch.toLowerCase()`) и давали URL с `x64` в пути, который goreleaser никогда не выпускает (он использует `amd64`).

**Что теперь есть:** `normaliseArch` приводит вход к нижнему регистру перед switch. Тесты покрывают входы в обоих регистрах.

**Правило:** когда пишете нормализатор, стоящий на двух соглашениях о регистре, нормализуйте регистр в начале функции. Не полагайтесь на то, что вызывающие передадут «правильный» регистр.

## 14. Контекст был расширяемым до v0.7.0 и молча терял данные

**Симптом (до v0.7.0):** пользователь пишет `context.role: "public API"` или `context.callers: [...]` в спецификации. `specter parse` проходит. Нижестоящие инструменты видят только объявленные поля (`system`, `feature` и т.п.), лишние ключи исчезли.

**Причина:** в схеме было `context.additionalProperties: true` («дополнения допустимы»), но `SpecContext` (types.go) был закрытой структурой. Нестрогий по умолчанию unmarshal в yaml.v3 молча отбрасывал всё, чего структура не объявляла. Обещание схемы и поведение типов расходились, и расхождение было невидимым.

**Что теперь есть (v0.7.0+):** `context.additionalProperties: false`. Неизвестные ключи контекста отклоняются при парсинге с именованной ошибкой. SPEC_SCHEMA_REFERENCE.md больше не рекламирует лазейку «добавляйте свои ключи».

**Правило:** когда JSON Schema объявляет `additionalProperties: true` у объекта, который types.go парсит в закрытую структуру, несоответствие вызывает тихую потерю данных. Либо делайте схему строгой (предпочтительно, начиная с v0.7.0), либо парсите в `map[string]interface{}` в структуре (используется для `inputs` и `expected_output`, которые по замыслу свободной формы).

## 15. Имена релизных ассетов НЕ совпадают с выводом `uname`

**Симптом:** документы (и старый код расширения), использовавшие `$(uname -s)_$(uname -m)` или `specter_Linux_x86_64.tar.gz`, получают 404. При установке пользователи получают 9-байтовый ответ `Not Found`, записанный на диск и сделанный +x.

**Причина:** в проекте сосуществуют четыре разных словаря архитектур/ОС:

| Источник | ОС на Linux amd64 | Архитектура на Linux amd64 |
|---|---|---|
| `uname -s` / `uname -m` | `Linux` | `x86_64` |
| Node `process.platform` / `process.arch` | `linux` | `x64` |
| VS Code `runner.os` / `runner.arch` | `Linux` | `X64` |
| **Go `GOOS` / `GOARCH` (имена ассетов)** | **`linux`** | **`amd64`** |

goreleaser использует `name_template: "{{ .ProjectName }}_{{ .Version }}_{{ .Os }}_{{ .Arch }}"`, значения Go, поэтому каждый ассет — `specter_<version>_<linux|darwin|windows>_<amd64|arm64>.<ext>`. Ни одно из соглашений источников не совпадает напрямую; каждый вызывающий установщик должен переводить.

**Что теперь есть:** все фрагменты установки в README.md, QUICKSTART.md, GETTING_STARTED.md переводят `uname` в `GOOS`/`GOARCH` и разрешают версию через GitHub API. `normaliseArch` расширения VS Code приводит вход к нижнему регистру, поэтому обрабатывает и верхний (runner.arch), и нижний (process.arch). Композитный GitHub Action в `.github/actions/specter-sync/action.yml` тоже выполняет перевод.

**Правило:** когда пишете любой пример команды установки, никогда не используйте `uname -m`, `uname -s`, `process.arch` или `runner.arch` сырыми в URL. Всегда переводите. И никогда не опускайте версию: безверсионного псевдонима нет (goreleaser можно настроить на его выпуск, но сейчас он этого не делает).

## 16. `path.dirname()` от пути каталога возвращает РОДИТЕЛЯ, а не каталог

**Симптом:** расширение VS Code сообщает «no specter.yaml found in this workspace», хотя `specter.yaml` лежит в корне рабочего пространства. `specter init` создаёт файл, перезагрузка не помогает, `specter init --force` не помогает.

**Причина:** `resolveManifestPath(filePath, exists)` в `activation.ts` начинал поиск с вызова `path.dirname(filePath)`. Функция была задумана для вызова с путём ФАЙЛА (например, `/project/specs/auth.spec.yaml`), где `dirname` корректно отбрасывает имя файла, оставляя `/project/specs/`. Все модульные тесты передавали пути файлов.

Но реальный вызывающий в `setupFolder` передаёт `folder.uri.fsPath` — путь КАТАЛОГА, вроде `/home/user/project`. `path.dirname` не проверяет, является ли вход каталогом; он работает синтаксически. `path.dirname("/home/user/project")` возвращает `/home/user` — РОДИТЕЛЬСКИЙ каталог. Затем резолвер искал `/home/user/project/../specter.yaml`, `/home/user/specter.yaml` и т.д., доходя до `/`, **никогда не проверяя сам `/home/user/project/specter.yaml`**.

Это вышло в spec-vscode v1.0 и затронуло каждого пользователя, у кого `specter.yaml` лежал в корне рабочего пространства — каноническом месте, которое документы явно рекомендуют. Модульные тесты покрывали задуманное соглашение вызова (пути файлов), но не реальное соглашение в продакшене (пути каталогов).

**Что теперь есть (v0.8.1+):** `resolveManifestPath` принимает необязательный третий аргумент `isDirectory: (p: string) => boolean`, чтобы вызывающие, работающие с папками рабочего пространства, могли сказать «этот путь И ЕСТЬ стартовый каталог». Вызывающий в рантайме передаёт проверку `statSync(...).isDirectory()`. Два регрессионных теста закрепляют обе формы.

**Правило:** `path.dirname` работает со строками, а не с типами файловой системы. Если функция принимает «путь», не уточняя какой, исходите из того, что хотя бы один реальный вызывающий передаст каталог. Либо ограничьте контракт (назовите её `resolveManifestFromFile`), либо принимайте оба и ветвитесь по явному предикату.

## 17. Расширение выдумало флаги CLI, которых бинарник никогда не принимал

**Симптом (v0.8.1):** прогон покрытия падает с `error: unknown flag: --manifest`. Также затронуты вызовы `parse` и `check` из расширения.

**Причина:** `SpecterClient` в `client.ts` был построен в предположении, что у CLI есть флаги, которые никогда не выпускались:

- `specter parse --json --manifest <path>` — флага `--manifest` не существует
- `specter check --json --manifest <path>` — то же
- `specter coverage --json --manifest <path> [--spec <id>]` — то же, плюс `--spec` тоже не существует
- `specter diff --json --base <ref> <file>` — нет `--base`, нет `--json`; diff принимает два позиционных аргумента `<path>[@<ref>]` и выдаёт человекочитаемый текст

Пять выдуманных флагов в продакшн-коде. CLI отклоняет неизвестные флаги (поведение Cobra по умолчанию), поэтому каждый вызов бросал исключение, которое try/catch в `runCoverageForFolder` показывал как «no coverage data» в боковой панели. Пользователи видели пустое состояние покрытия независимо от валидности их спецификаций.

**Почему проскочило:** ни один интеграционный тест расширения никогда не вызывал реальный бинарник CLI. Все тесты были модульными, против TypeScript-моков контракта CLI. Моки описывали, что расширение *хотело*, чтобы CLI принимал, а не что он реально принимал.

**Что теперь есть (v0.8.2+):** флаги `--manifest` / `--spec` / `--base` / `--json` (у diff) вырезаны из `SpecterClient`. Вместо этого `execFile` вызывается с `cwd: path.dirname(manifestPath)`, чтобы собственный обход `findManifest` в CLI нашёл правильный `specter.yaml`. Новый интеграционный набор `client.test.ts` запускает реальный собранный CLI против временного рабочего пространства и утверждает, что каждый публичный метод работает без исключений. Набор пропускается, когда `bin/specter` не существует (до сборки), поэтому CI требует этапа сборки первым.

**Правило:** любой код, вызывающий другой бинарник через оболочку, получает хотя бы один интеграционный тест, запускающий реальный бинарник. Моки описывают замысел, а не контракт. Если CI не проходит путь реального бинарника, каждый флаг — догадка.

## 18. Marketplace НЕ является тестовым стендом (люди должны проверить перед публикацией)

**Симптом:** четыре патч-релиза расширения VS Code за один день (v0.8.0, v0.8.1, v0.8.2 и v0.8.3), каждый исправлял баг, который первый реальный пользователь находил сразу после установки. Пользователи видят уведомление об автообновлении каждые несколько часов, и каждая установка вскрывает очередную регрессию. Это бьёт по доверию.

**Причина:** цикл до публикации был таким:
1. Написать код
2. Запустить `make check` + `npx jest`
3. `vsce package` + `vsce publish`
4. Ждать, пока пользователь установит и сообщит, что сломалось

Шаг 4 и был тестом. Модульные тесты покрывали примерно 30% реальной пользовательской поверхности расширения, а именно чистые функции. Непокрытые 70% (разрешение бинарника, отрисовка дерева, вызов CLI, гонки активации, предположения о cwd) — там и жили все четыре бага v0.8.x.

Урок не только «писать больше модульных тестов»: реальным пробелом было отсутствие проверенного человеком сквозного теста в настоящем окне VS Code против настоящего рабочего пространства перед каждой публикацией. Не мок, не замена в CI, не «я уверен, что работает», а реальная установка + перезагрузка + прокликивание.

**Что теперь есть (v0.8.3+):**
- `RELEASING.md` описывает шлюз из 8 шагов. Обязателен перед любым `vsce publish`.
- `make release-check` упаковывает VSIX и печатает чек-лист. Он не запускает `vsce publish` — это остаётся ручным, чтобы оператор не мог забыть шаг 7 (человеческое одобрение).
- Безголовые интеграционные тесты `@vscode/test-electron` — запланированная долгосрочная страховка.

**Правило:** Marketplace — канал распространения, а не тестовый стенд. Каждая публикация должна нести поведение, уже проверенное человеком в живом окне VS Code. Агент может запустить проверки и приложить доказательства (скриншот, записанную сессию или воспроизводимый скрипт). Человек всё равно выполняет шаг 7 из `RELEASING.md` и одобряет. Первый установивший пользователь должен стать сто первым человеком, увидевшим работающую функцию, а не первым.

## 19. Публикуйте VSIX только после того, как существует релиз CLI, который он скачивает

**Симптом:** расширение v0.6.5 запрашивает `api.github.com/.../releases/latest`, получает, например, v0.6.5, затем пытается скачать `.../releases/download/v0.6.5/...`. Если релиз GitHub для этого тега ещё не существует, в теле будет 404 «Not Found» (см. #3).

**Что теперь есть (v0.15.2+):** версия расширения больше не обязана совпадать с версией CLI; v0.15.2 был релизом только расширения. Каждая сборка объявляет CLI, который скачивает, в `specterCli.default` в `vscode-extension/package.json`, и `cliDefault.test.ts` падает, когда это значение отличается от `VERSION`. По умолчанию расширение скачивает именно эту версию, а не `releases/latest`, в свою приватную копию в `~/.specter/cli/`.

**Правило:** сначала запушьте тег CLI и дождитесь завершения workflow релиза. Загрузке нужны архив и `checksums.txt`, которые GoReleaser публикует для `specterCli.default`. Только затем публикуйте VSIX в Marketplace. Если VSIX живёт до релиза, его загрузка приватной копии CLI падает у каждого пользователя, у кого нет CLI в диапазоне `specterCli.range` в PATH или в `~/.specter/bin`. Две настройки это обходят: `specter.binaryPath` на существующий файл или `specter.version`, привязанный к опубликованной версии либо `latest`. Привязка к невыпущенной версии падает так же.
