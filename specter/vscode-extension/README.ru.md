# Specter SDD для VS Code

**Внесите цикл «спецификация, тест, реализация» в свой редактор.**

В разработке через спецификации источник истины — спецификация, а не код. Тесты прослеживаются к критериям приёмки через аннотации `@spec` и `@ac`, и каждая спецификация должна достичь своего порога tier, прежде чем конвейер пройдёт. Это расширение делает эту дисциплину видимой и удобной: вы видите, что покрыто, что дрейфует и что нужно вашему ИИ-ассистенту, не переключая окна.

## Замысел человека, исполнение ИИ

Схема Specter намеренно подробна: ограничения, критерии приёмки, tiers, происхождение, пороги покрытия. Писать всё это вручную для каждого модуля было бы непрактично, и это никогда не было замыслом.

Задуманный процесс — сотрудничество между вами и вашим ИИ-ассистентом:

1. **Вы даёте замысел**: краткое описание того, что должен делать модуль, его ключевые ограничения и любые неочевидные суждения или компромиссы
2. **ИИ пишет спецификацию**, переводя ваш замысел в полностью структурированный файл `.spec.yaml` с ограничениями, AC и назначением tier
3. **ИИ пишет тесты**, выведенные напрямую из AC в спецификации
4. **Вы проверяете**: спецификация и тесты — шлюз одобрения; вы подтверждаете, что ИИ правильно зафиксировал ваш замысел, до начала любой реализации
5. **ИИ реализует**: спецификация как контракт, тесты как проверка

Specter проверяет артефакты перед собой, а не порядок, в котором вы их писали. Он проверяет, что каждая спецификация парсится и разрешается. Он измеряет покрытие по аннотациям `@spec` и `@ac` в ваших тестах. По умолчанию он засчитывает аннотированный критерий, только если его тест прошёл, в результатах, которые вы загружаете через `specter ingest`. Он валит `specter sync`, когда спецификация ниже своего порогового tier. Это делает правила инфраструктурой, а не пожеланием.

**Основная миссия: провести ваш ИИ-ассистент через спецификацию, тесты, реализацию и оценку в правильном порядке, каждый раз, с сохранением вашего замысла на всём пути.**

## Какую проблему это решает

Когда вы работаете с ИИ-инструментами для кода, две вещи ломаются тихо:

**Пробелы покрытия, которых вы не видите.** Вы пишете спецификацию с восемью требованиями. ИИ реализует шесть. Тесты для этих шести проходят. Остальные два просто отсутствуют — без ошибки, без предупреждения, без индикатора где-либо. Вы узнаёте в продакшене.

**Спецификации, которые меняются после написания тестов.** Требование уточняют, ужесточают или удаляют. Тест, который его покрывал, всё ещё говорит `@ac AC-03`. Эта аннотация теперь ложь: она ссылается на требование, которое больше не значит того же. Никто не замечает.

Specter SDD показывает обе проблемы в редакторе, постоянно, по мере работы.

## Возможности

### Знайте, что покрыто, не запуская отчёт

CodeLens над каждым требованием в файле спецификации сообщает, покрывает ли его тест: галочка, когда покрывает хотя бы один, перечёркнутый круг, когда ни один. Состояний два, а не три. Более ранняя версия этой страницы обещала серое состояние «намеренно исключено», и spec-vscode 5.0.0 отозвала его: `coverage --json` не выдаёт такой классификации, поэтому расширению не из чего её отрисовать. Боковая панель Coverage показывает те же два состояния зелёной и красной иконками, а строка состояния показывает агрегат по всем спецификациям.

### Ловите ошибки спецификации при сохранении

Ошибки схемы в файлах `.spec.yaml`, например отсутствующие обязательные поля, появляются в панели Problems при сохранении файла. При включённом автосохранении это вскоре после того, как вы перестанете печатать. Битые межспецификационные ссылки и осиротевшие ограничения также появляются при сохранении.

### Пишите аннотации `@spec` и `@ac` за секунды

Наберите `// @spec` в тестовом файле, и Specter предложит имена спецификаций, ранжированные по близости файла спецификации к вашему тестовому файлу. Наберите `// @ac` на следующей строке, и варианты будут ограничены только требованиями из спецификации, на которую вы только что сослались. Без запоминания ID, без переключения на другой файл.

### Смотрите полное требование при наведении

Наведите на `// @ac AC-03` в тесте, чтобы увидеть полное описание требования, его текущий статус покрытия и какие другие тестовые файлы его также покрывают. Наведите на ID ограничения в спецификации, чтобы увидеть, какие требования от него зависят и покрыты ли они.

### Получайте предупреждение, когда спецификация меняется под вашими тестами

Если требование спецификации меняется после того, как вы аннотировали против него тест, inline после аннотации появляется **предупреждение о дрейфе** с текстом `spec changed` и маркером в линейке обзора у правого края редактора. Наведите, чтобы увидеть исходное требование и текущее рядом, с классификацией: ломающее изменение, добавление или уточнение формулировки.

### Навигируйте по спецификациям как по коду

Переход к определению работает по перекрёстным ссылкам спецификаций: перейдите от ссылки `depends_on` к целевому файлу спецификации или от ссылки на ограничение к точной строке, где оно объявлено.

### Видьте полную картину, когда что-то падает

Откройте боковую панель Specter, чтобы просматривать спецификации, их требования и покрывающие их тестовые файлы в дереве. Когда что-то ниже порога, панель Insights показывает объяснение простым языком: что не покрыто, что на самом деле говорят требования и какие ограничения затронуты.

### Передайте ИИ весь контракт

**Specter: Copy Spec Context for AI** форматирует текущую спецификацию, tier, ограничения и все требования с полными описаниями в структурированный markdown-блок и копирует его в буфер обмена. Вставляйте в Claude, Cursor или Copilot, чтобы ИИ начинал с контракта, а не с догадки.

### Получайте предложения аннотаций автоматически

Над любой тестовой функцией, ещё не связанной со спецификацией, появляется подсказка с наиболее релевантными требованиями на основе имени и тела теста. Всё работает локально, без вызовов API и сетевого доступа. Нажмите, чтобы вставить аннотацию.

## Как процесс SDD выглядит в VS Code

**1. Напишите спецификацию.** Создайте файл `.spec.yaml`. Specter проверит его при сохранении, а ошибки схемы появятся в панели Problems.

**2. Аннотируйте тест.** Используйте автодополнение `// @spec` и `// @ac`, чтобы связать тестовую функцию с требованием. CodeLens над этим требованием превратится в галочку.

**3. Реализуйте по контракту.** Перед промптом ИИ-ассистенту выполните **Copy Spec Context for AI**. Он получит точные требования и ограничения, а не пересказ.

**4. Сразу видьте пробелы.** Любое требование, всё ещё показывающее перечёркнутый круг после реализации, — пробел покрытия. Строка состояния показывает количество. Панель Insights объясняет, чего не хватает.

**5. Оставайтесь согласованными по мере эволюции спецификаций.** Когда спецификация меняется, предупреждения о дрейфе появляются у любого теста, чья аннотация теперь ссылается на иное требование, чем при написании.

## Требования

- VS Code 1.85 или новее
- Рабочее пространство, содержащее `specter.yaml` или хотя бы один файл `*.spec.yaml`
- Бинарник `specter`. Расширение скачивает его при первом использовании, когда в PATH или в `~/.specter/bin/specter` нет поддерживаемой версии. Оно не делает этого, когда `specter.binaryPath` указывает на существующий файл или `specter.autoDownload` равен false.

## Формат аннотаций

```typescript
// @spec payment-create-intent
// @ac AC-01
function testValidCurrencyCreatesIntent() {
  const result = createIntent({ currency: 'USD', amount: 1000 });
  expect(result.status).toBe('pending');
}
```

Аннотации — обычные комментарии: без шага сборки, без фреймворка, работает на любом языке.

## Настройки

| Настройка | По умолчанию | Описание |
|---|---|---|
| `specter.binaryPath` | `""` | Путь к бинарнику specter. Оставьте пустым для авторазрешения: CLI в PATH или в `~/.specter/bin/specter` используется, когда его версия поддерживается расширением, иначе расширение использует собственную копию в `~/.specter/cli`. Путь, заданный здесь, должен быть работающим бинарником, отвечающим на `--version`, но он не сверяется с поддерживаемым диапазоном, потому что это ваш явный выбор. Несуществующий путь игнорируется, и разрешение продолжается. Машинная область; настройки рабочего пространства игнорируются. |
| `specter.autoDownload` | `true` | Скачивать собственную копию CLI расширения, когда поддерживаемый CLI не найден. |
| `specter.version` | `""` | Версия собственной копии CLI расширения. Пусто означает версию CLI, объявленную этой сборкой расширения, которая может отличаться от версии самого расширения; `latest` отслеживает новейший релиз GitHub. Поддерживаемый CLI в PATH используется в любом случае. Машинная область; настройки рабочего пространства игнорируются. |
| `specter.showInsightsOnFailure` | `true` | Автоматически открывать панель Insights, когда спецификация не проходит порог. |

## Использование `specter` из внешних терминалов

Расширение держит собственную копию CLI в `~/.specter/cli`, один файл на версию, и никогда не меняет установленный вами CLI. `~/.specter/bin/specter` — ваш: расширение создаёт его, только когда вы запускаете команду shell PATH и там ничего нет, и после этого никогда не заменяет. Встроенный терминал VS Code получает `~/.specter/bin` в начало PATH автоматически. Внешние терминалы (iTerm, Windows Terminal, tmux и т.п.) — нет, там понадобится полный путь. Если у вас нет собственного CLI в PATH, чтобы набрать `specter` там, нужна эта копия, поэтому один раз запустите команду shell PATH. Собственные команды расширения, открывающие терминал, например Run Reverse Compiler и View Diff, используют CLI, который разрешило расширение, и не требуют настройки.

Один раз выполните `Specter: Add CLI to Shell PATH` из командной палитры, и расширение добавит идемпотентный export в rc-файл вашей оболочки (`.bashrc` в Linux, `.bash_profile` в macOS, `.zshrc` для zsh, `config.fish` для fish). Перезапустите терминал, и `specter` работает откуда угодно.

Команда идемпотентна: повторный запуск при уже установленном пути сообщает об этом и ничего не меняет.
