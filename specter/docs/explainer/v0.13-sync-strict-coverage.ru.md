# Почему `specter sync` теперь требует файл результатов (v0.13)

**Для кого:** команды, обновляющиеся с v0.12.x до v0.13.x, у которых `specter sync` внезапно падает на чистом чекауте.
**Что изменилось:** в v0.13 фаза покрытия в `sync` учитывает вашу настройку `strictness`, а настройка по умолчанию (`threshold`) требует `.specter-results.json`.
**Что делать:** выберите одно из трёх исправлений в разделе [Что делать](#что-делать). Рекомендуемое — изменение одного флага.

---

## Симптом

Вы обновляете Specter с релиза v0.12.x до v0.13.x. `specter sync`, который раньше проходил на свежем чекауте, теперь останавливается на фазе покрытия:

```
Specter Sync

  PASS parse: 111 spec(s) parsed successfully
  PASS resolve: 111 specs, 43 dependencies resolved
  PASS check: 0 warning(s), 0 info
  FAIL coverage: strictness "threshold" requires .specter-results.json — run 'specter ingest' first, or use --strictness annotation for structural coverage

Pipeline failed at coverage phase.
```

Код выхода `1`. Запустите `specter ingest` (напрямую или через цель результатов тестов, используемую вашим проектом), чтобы появился `.specter-results.json`, и тот же `specter sync` снова пройдёт. Или, если хотите, чтобы `sync` оставался запускаемым на чистом дереве, добавьте `--strictness annotation` (см. [Что делать](#что-делать)).

> Более ранние патчи v0.13 формулировали это сообщение как `--strict requires .specter-results.json — run 'specter ingest' first`. Причина и исправления идентичны; уточнена только формулировка, чтобы называть активный режим строгости и альтернативу `--strictness annotation`.

Это не падение и не потеря данных. Это `sync`, обеспечивающий гарантию, которую он не мог обеспечить до v0.13. Остальная часть страницы объясняет почему, что вас удивило и как получить желаемое поведение.

---

## Предыстория: два способа измерять покрытие

Specter может решать, «покрыт» ли критерий приёмки (AC), двумя способами.

- **Структурное покрытие (по аннотациям)**: AC покрыт, когда тест несёт его аннотацию `// @ac AC-NN`. Specter считает аннотации. Он **не** спрашивает, прошёл ли тест. Это не требует результатов тестов, поэтому работает на чистом чекауте.
- **Покрытие по исходу (строгое)**: AC покрыт, только когда его аннотированный тест действительно **прошёл** в последнем прогоне. Падающий, пропущенный или упавший с ошибкой тест понижает AC до непокрытого. Это требует файла результатов `.specter-results.json`, созданного `specter ingest` из вывода вашего раннера тестов.

Покрытие по исходу — более сильная гарантия. Именно ради неё существуют `specter ingest` и `coverage --strict` (см. [Покрытие под контролем CI](v0.10-ci-gated-coverage.ru.md)). Структурное покрытие говорит лишь «кто-то написал тест для AC-07». Покрытие по исходу говорит «тест для AC-07 выполнился и прошёл».

Какой из них применяется, управляется одной настройкой: `strictness`.

---

## Настройка `strictness`

`strictness` живёт в `specter.yaml` в разделе `settings` и может быть переопределена для команды через `--strictness`. У неё три значения:

| Значение | Режим покрытия | Нужен `.specter-results.json`? |
|---|---|---|
| `annotation` | структурный: считает аннотации | Нет |
| `threshold` | по исходу: падающие/пропущенные тесты понижают, применяются пороги по tier | **Да** |
| `zero-tolerance` | по исходу: строжайший; любой пробел валит | **Да** |

**Значение по умолчанию, когда `strictness` не задана, — `threshold`.** Этот единственный факт и есть источник удивления. Вам не нужно нигде писать `strictness: threshold`, чтобы получить новое поведение; если её опустить, вы тоже получите `threshold`.

---

## Что на самом деле изменилось между v0.12 и v0.13

Настройка `strictness` появилась в v0.11, но до v0.12 включительно она применялась лишь частично. `coverage` учитывал её для кодов выхода zero-tolerance, а явный флаг `--strict` включал покрытие по исходу, тогда как команда `sync` тихо игнорировала настройку целиком: фаза покрытия в `sync` всегда шла структурным путём, независимо от значения `strictness`. (Полная маршрутизация `--strictness threshold` через строгий путь отчёта в самом `coverage` появилась в spec-coverage 1.15.0.) Значит, на v0.12:

- `specter coverage --strict` обеспечивал покрытие по исходу и требовал файл результатов.
- `specter sync` — **нет**; он считал аннотации и проходил на чистом дереве.

Это разделение было пробелом, а не функцией. `sync` документирован как одношаговый шлюз CI (`parse → resolve → check → coverage`). Если вы ставили `strictness: threshold`, ожидая, что покрытие будет гейтироваться по исходу, `sync` тихо давал более слабую проверку, чем `coverage`. Конвейер мог быть зелёным в `sync`, пока `coverage --strict` был красным на том же дереве.

v0.13 закрыл пробел. Фаза покрытия в `sync` теперь идёт через ту же строгую логику, что `coverage`. Под `threshold` или `zero-tolerance` (что, повторюсь, включает значение по умолчанию) отсутствующий `.specter-results.json` — жёсткий отказ:

```
strictness "threshold" requires .specter-results.json — run 'specter ingest' first, or use --strictness annotation for structural coverage
```

Сообщение называет режим строгости, вызвавший отказ (здесь — значение по умолчанию `threshold`), а не флаг `--strict`, который вы не передавали, и указывает оба исправления. `coverage --strict` сохраняет свою формулировку (`--strict requires .specter-results.json …`), потому что там вы действительно передали `--strict`.

В режиме `annotation` отсутствующий файл результатов — **не** ошибка; структурный путь работает как раньше.

Замысел: `sync` и `coverage` должны значить одно и то же. Если ваш `strictness` говорит «покрытие по исходу», каждая команда, сообщающая покрытие, должна обеспечивать покрытие по исходу, включая `sync`. Молчаливый откат `sync` к подсчёту аннотаций позволил бы команде выпустить сломанный конвейер, веря, что она защищена. Это то же рассуждение, по которому `coverage --strict` отказывается работать без результатов.

## Побочный эффект, который вас задел

Изменение правильное, но у него есть реальное и неудобное следствие: **`sync` больше не запускается на чистом чекауте при настройках по умолчанию.**

До v0.13 первой командой в цикле разработки мог быть `specter sync`, запущенный до выполнения каких-либо тестов. Теперь при значении по умолчанию `threshold` тот же `sync` падает, потому что ни один прогон тестов ещё не создал `.specter-results.json`. Естественная проверка «целы ли мои спецификации и граф?» теперь зависит от файла, который существует только после прогона тестов и приёма результатов.

Это также создаёт **расхождение локально и в CI** при частичном обновлении. Если ваш CI закреплён на v0.12.x, задача `sync` в CI всё ещё использует старый структурный путь и остаётся зелёной, а участник, обновившийся локально до v0.13.x, видит падение `sync` на том же чистом дереве. Поведение разошлось не потому, что кто-то поменял ваш конфиг; оно разошлось потому, что две машины запускают разные версии Specter, трактующие одну и ту же `strictness: threshold` по-разному.

Исправление расхождения — перестать стоять на двух версиях: **закрепите одну и ту же версию Specter в CI и в окружении участников**, затем сделайте каждый голый вызов `specter sync` (в `Makefile` и CI) одним из вариантов ниже — сначала ingest или `--strictness annotation`. Повышать пин с v0.12.x до v0.13.x безопасно *после* обновления этих вызовов, а не до.

> Примечание: `.specter-results.json` обычно в git-ignore, поэтому в свежем чекауте его никогда нет. Это сделано намеренно, но именно поэтому `sync` при строгом значении по умолчанию падает при первом запуске.

## Что делать

Три варианта. Они не эквивалентны: первый сохраняет гарантию покрытия по исходу, остальные её обменивают или переносят. Выбирайте по тому, что вы хотите, чтобы `sync` означал.

### Вариант 1: остаться строгим, сначала создать файл результатов (рекомендуется для шлюзов CI)

Если вы хотите, чтобы `sync` продолжал обеспечивать покрытие по исходу, дайте ему файл результатов. Запустите тесты, примите их, затем синхронизируйте:

```bash
go test -json ./... > go-results.json
specter ingest --go-test go-results.json   # writes .specter-results.json
specter sync                                # coverage phase now has its inputs
```

В большинстве проектов уже есть make-цель или шаг CI, выполняющий ingest. Запустите его перед `sync`. Это сохраняет самую сильную гарантию: падающий или пропущенный аннотированный тест корректно провалит конвейер.

### Вариант 2: разделить быстрый структурный шлюз и строгий шлюз (рекомендуется для цикла разработки)

Если вы хотите, чтобы `sync` был быстрой проверкой «целы ли мои спецификации?», работающей на чистом дереве, **и** при этом хотите принуждение по исходу, запускайте два отдельных шага. Сделайте `sync` структурным явным переопределением, а строгую проверку вынесите в отдельный шаг, который сначала делает ingest:

```bash
# Fast gate: runs on a clean checkout, no results file needed
specter sync --strictness annotation

# Strict gate: separate step, after tests have run and been ingested
specter ingest --go-test go-results.json
specter coverage --strict
```

Это шаблон, который Specter использует на собственном репозитории: его CI запускает `specter sync --strictness annotation` для структурного шлюза и отдельный шаг `coverage --strict` для шлюза по исходу. Вы получаете обе гарантии, и ни один шаг не блокирует другой. `--strictness annotation` влияет только на этот вызов и не трогает значение по умолчанию в `specter.yaml`.

Цена разделения — одна дополнительная команда: ваш `sync` для разработки больше не даёт покрытие по исходу одним шагом. `sync` отвечает «целы ли мои спецификации?», а отдельный строгий шаг — «прошли ли аннотированные тесты?» — два прогона вместо одного. Для большинства циклов это честный обмен за `sync`, работающий на чистом дереве; если вы предпочитаете одну команду, используйте вариант 1.

### Вариант 3: изменить значение по умолчанию в `specter.yaml`

Вы можете вернуть проекту структурное поведение по умолчанию везде:

```yaml
# specter.yaml
settings:
  strictness: annotation
```

Тогда `sync` и `coverage` оба работают структурно без флагов. **Осознайте цену:** вы отключаете покрытие по исходу для всего проекта. Падающие и пропущенные аннотированные тесты снова будут считаться покрытыми — ровно тот пробел, ради закрытия которого строился `coverage --strict`. Выбирайте это, только если вам действительно не нужно покрытие, гейтируемое по исходу. Если оно нужно хоть где-то, предпочтите вариант 2.

---

## Как выбирать

- Вы хотите, чтобы `sync` был вашим единственным шлюзом CI, и вы уже принимаете результаты тестов → **вариант 1.**
- Вы хотите быстрый `sync` на чистом дереве *и* настоящую проверку по исходу → **вариант 2.** Это самый частый правильный ответ.
- Вам вообще не нужно покрытие по исходу → **вариант 3.**

Если ваш CI всё ещё закреплён на v0.12.x и вы решаете, двигать ли пин на v0.13.x: пин безопасно двигать, когда ваш шаг `sync` — один из вариантов выше. Падение пина на v0.13.x не регрессия, которую надо переждать; это новый контракт, говорящий, что шагу нужен файл результатов или явный `--strictness annotation`.

## Краткая справка

| Ситуация | Результат под v0.13 |
|---|---|
| `specter sync`, нет strictness в `specter.yaml`, нет файла результатов | **Падает** на покрытии (по умолчанию `threshold`) |
| `specter sync`, `strictness: threshold`, нет файла результатов | **Падает** на покрытии |
| `specter sync`, `strictness: zero-tolerance`, нет файла результатов | **Падает** на покрытии |
| `specter sync --strictness annotation`, нет файла результатов | Проходит (структурное покрытие) |
| `specter sync`, любой строгий режим, файл результатов есть | Проходит/падает по реальным исходам тестов |
| `specter sync`, `strictness: annotation`, нет файла результатов | Проходит (структурное покрытие) |

Сообщение об ошибке `strictness "<mode>" requires .specter-results.json — run 'specter ingest' first, or use --strictness annotation for structural coverage` всегда значит одно: активен строгий режим, а файла результатов нет. Исправление всегда одно из: создать файл (`ingest`) или включить для этого вызова `--strictness annotation`. (Более ранние патчи v0.13 формулировали его как `--strict requires .specter-results.json …`.)

О самой машинерии покрытия по исходу см. [Покрытие под контролем CI](v0.10-ci-gated-coverage.ru.md). Полный справочник флагов и настроек — в [`CLI_REFERENCE.md`](../CLI_REFERENCE.ru.md).
