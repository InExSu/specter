# v0.11: дисциплина ИИ-цикла + упрочение внедрения

**Для кого:** команды, запускающие Specter на реальной кодовой базе, и их ИИ-ассистенты (Claude, Codex, Cursor, Copilot, Gemini CLI).
**Что вышло:** набор `specter explain`, `specter check --test`, `specter init --install-hook`, `specter init --ai <tool>`, трёхуровневый шлюз `settings.strictness`, плюс четыре исправления по issue от реальных пользователей.
**Что закрывает:** разрыв между «у Specter правильное мнение» и «ИИ / разработчик / конвейер CI это мнение действительно соблюдает».

---

## Зачем это существует

v0.10 закрыл дыру фазы оценки: исход теста теперь механический, а не обещание. Следующий пробел — порядок операций. Тесты пишут, но не до кода. ИИ-ассистенты генерируют правдоподобный код, не читая спецификацию. CI замечает отсутствие аннотации теста только после того, как разработчик уже запушил. Манифесты молча принимают опечатки. Пустое обнаружение тестов молча сообщает 0% покрытия.

Каждый из этих пробелов мал. Вместе они означают, что зелёный прогон CI может скрывать реальную проблему внедрения. v0.11 их закрывает.

## 1. Набор `specter explain`

`explain` уже был диагностикой только для чтения вида `<spec-id>:<AC-NN>`. v0.11 добавляет три новые поверхности, все только в stdout.

```bash
specter explain annotation                         # test-annotation reference
specter explain schema                             # full schema field reference
specter explain schema spec.acceptance_criteria.items.approval_gate  # one field
specter explain spec-coverage                      # spec card: tier, coverage %, per-AC test files
```

Обходчик схемы разрешает JSON `$ref`, поэтому вложенные поля под `spec.acceptance_criteria.items.*` и `spec.constraints.items.*` показываются рядом с полями верхнего уровня. `explain schema <unknown-path>` возвращает ненулевой код выхода с подсказкой `did you mean?` в пределах расстояния Левенштейна 3.

Карточка спецификации без AC (`specter explain spec-coverage`) заменяет двухколоночный список COVERED/UNCOVERED из v1.0. Теперь она показывает tier, процент покрытия и тестовые файлы, покрывающие каждый AC, так что «где тестируется AC-19?» — одна команда вместо grep.

Это поверхности, к которым ИИ-ассистент должен обращаться по требованию, а не полагаться на заранее загруженное содержимое спецификации в своём контекстном окне. В паре с `init --ai <tool>` (ниже), который пишет файл инструкций, велящий ИИ *вызывать* `specter explain`, а не догадываться.

## 2. `specter check --test` (`-t`): перекрёстная проверка аннотаций тестов

`specter check` уже валидирует структуру со стороны спецификации (осиротевшие ограничения, структурные конфликты, классификация повышения версии). v0.11 добавляет аналог со стороны тестов:

```bash
specter check --test    # opt-in for v0.11; default-on candidate later
```

Три вида диагностик:

- **`unknown_spec_ref`**: `// @spec foo` в тесте, где спецификации с таким id не существует.
- **`unknown_ac_ref`**: `// @spec real-spec` + `// @ac AC-99`, где `real-spec` не объявляет AC-99.
- **`malformed_ac_id`**: ID, не проходящие `^AC-\d{2,}$`: `AC-1` (без дополнения нулями), `ac-01` (неверный регистр), `AC-1A` (суффикс).

Каждая диагностика называет файл, строку и ссылку. Правило каскада: когда `@spec` неизвестен, дочерние строки `@ac` под ним отдельно не проверяются. Аннотации внутри многострочных строковых литералов (шаблонные строки TS, тройные кавычки Python) — данные, а не настоящие аннотации. Сканер их пропускает.

`specter sync --strict` автоматически проводит проверку, поэтому CI ловит сломанные аннотации до мержа. Это делает флаг, а не манифест: `settings.strict: true` повышает диагностики warning и info до error и не запускает это сканирование. Раньше запускал, и это было дефектом. Настройка серьёзности, решающая, какие дефекты обнаруживаются, означала, что удаление одного ключа манифеста делало сломанную аннотацию невидимой, поэтому теперь `settings.strict` управляет только серьёзностью. `spec-check` C-07 говорит, что он делает; C-09 называет, что включает сканирование.

Патч документации v0.10.1 мог только предупреждать об этом классе ошибок (дрейф аннотаций между тестами и спецификациями). v0.11 обеспечивает его во время CI.

## 3. `specter init --install-hook`: git-хук pre-push

Каждый push, меняющий файлы реализации, но не добавляющий и не обновляющий ни одной аннотации `@spec` / `@ac`, блокируется локально:

```bash
specter init --install-hook
# Writes .git/hooks/pre-push (mode 0755) wrapped in shell-comment fenced markers
# (# specter:begin v1 ... # specter:end) so future re-runs replace only the
# Specter-managed region: your hand-edits outside the fence survive.
```

Хук делегирует скрытой подкоманде `specter pre-push-check`, которая читает формат stdin pre-push от git, запускает `git diff` для каждой ссылки и выходит с ненулевым кодом на диффах только реализации. Изменения документации / спецификаций / тестов всегда проходят. Изменённый файл Go считается, только когда он отличается от своей запушенной базы после канонического форматирования, поэтому перегруппировка `goimports` или переформатирование `gofmt` не является изменением реализации. Файлы TypeScript, JavaScript, Python, Rust, Java, C и C++ считаются всегда, как и любой файл, который хук не может прочитать, и любой файл Go, который он не может разобрать. Диффы, затрагивающие реализацию И добавляющие дельту аннотаций (в любом тестовом файле), проходят.

Обход — стандартным `git push --no-verify`. Новые ветки без merge-base с `origin/HEAD` пропускаются (сравнивать не с чем; следующий push догонит).

Обеспечиваемая дисциплина — «каждое изменение кода прослеживается к аннотации теста, которая прослеживается к спецификации». Раньше ревьюеры отмечали это в комментариях PR; теперь хук блокирует это локально до push.

## 4. `specter init --ai <tool>`: файл инструкций для ИИ

Пять инструментов, одна команда на инструмент:

```bash
specter init --ai claude     # writes CLAUDE.md
specter init --ai codex      # writes AGENTS.md
specter init --ai cursor     # writes .cursor/rules/specter.md (creates parent dir)
specter init --ai copilot    # writes .github/copilot-instructions.md (capped at 4 KB)
specter init --ai gemini     # writes GEMINI.md
```

Тело обёрнуто маркерами `<!-- specter:begin v1 -->` / `<!-- specter:end -->`. Повторные запуски заменяют только огороженную область; всё, что вы написали вне маркеров, сохраняется побайтово.

Тело инструкции учит ИИ четырём вещам по порядку:

1. **Читать спецификацию до написания кода** (самопроверка перед началом). ИИ должен назвать, какие ID спецификации и ID AC затрагивает изменение, прежде чем выдавать код.
2. **Использовать аннотации соглашения A** (видимые раннеру spec-id/AC-NN в заголовке теста). Включает хорошие и плохие примеры для Go и TypeScript.
3. **Запускать `make dogfood-strict` (или эквивалент вашего проекта) перед объявлением работы готовой.**
4. **Спрашивать у Specter содержимое спецификации по требованию** через `specter explain <spec-id>`, `specter explain schema`, `specter explain annotation`, а не брать из заранее загруженного снимка в файле инструкций.

Тело намеренно **не** вываливает содержимое спецификаций. Рабочее пространство на 249 спецификаций дало бы `CLAUDE.md` на 10 000 строк, который меняется при каждой правке спецификации. Файл инструкций — руководство по проекту, а не справочник.

`--ai claude` проверяет наличие `AGENTS.md` и вместо встраивания тела пишет директиву импорта `@AGENTS.md`, избегая дублирования шаблона, когда один проект поставляет оба.

ИИ, прочитавший спецификацию, пишет другой код, чем не читавший. Файл инструкций — самый дешёвый способ сделать так, чтобы чтение произошло.

## 5. `settings.strictness`: трёхуровневый шлюз покрытия

У `coverage --strict` был один режим: понижать непройденные аннотированные AC, применять пороги tier, выходить при провале порога. v0.11 делает уровень явным в `specter.yaml`:

```yaml
settings:
  strictness: threshold     # annotation | threshold (default) | zero-tolerance
```

| Уровень | Поведение |
|---|---|
| `annotation` | Поведение до v0.10. Считает только аннотации `// @ac`; игнорирует `.specter-results.json`. `coverage --strict` отвергается как несовместимый. Для новых пользователей в процессе миграции. |
| `threshold` (по умолчанию) | Текущее поведение `--strict` из v0.10.x. Понижает непройденные аннотированные AC, затем применяет пороги tier. Спецификация проходит, если после понижения очищает свой порог tier. `approval_gate` — метаданные. |
| `zero-tolerance` | Строжайший. Любой аннотированный AC со `status != passed` даёт выход 2. Любой AC с `approval_gate: true` и незаданным `approval_date` даёт выход 3 (отдельный код выхода). Порог tier не важен: один падающий тест валит прогон. |

Переопределение на вызов — `--strictness <level>`. Флаг CLI и поле манифеста валидируются по одному перечислению; опечатки на любом слое дают ошибку с перечислением трёх допустимых значений.

«strict» смешивали с «порогом tier». Команда может разумно хотеть 100% покрытия при мягкой строгости (миграция) или 50% покрытия при нулевой терпимости (зрелые спецификации Tier 1). Три уровня разделяют эти намерения.

## 6. Упрочение поверхности настроек (закрывает GH #75, #76, #78)

Три реальные ошибки от пользователя Python на v0.10.2:

**#76, блок `specter.yaml settings:` молча принимал неизвестные ключи.** Пользователи писали `tests_glob: "tests/**/*.py"` (правдоподобное, но несуществующее имя ключа), не получали предупреждения, запускали `coverage --strict` и получали молчаливые 0%. v0.11 выдаёт ошибку с подсказкой «вы имели в виду?»:

Прогон теперь падает с ошибкой, называющей неизвестный ключ, предлагающей
ближайший допустимый и перечисляющей все ключи, которые принимает `settings:`.
Вывод здесь не цитируется: он содержит длинное тире, а стилевой шлюз этого документа
его запрещает, поэтому цитата пришлась бы изменённой и перестала быть настоящими байтами.
Запустите `specter check` на манифесте с плохим ключом, чтобы увидеть его.

**#78, нет `settings.tests_glob`.** Опечатка `test_glob:` выше на самом деле пыталась задать отсутствующее поле. v0.11 добавляет его:

```yaml
settings:
  tests_glob: "tests/**/*.py"           # string form
  # OR
  tests_glob:                           # list form
    - "backend/**/*_test.go"
    - "frontend/**/*.test.ts"
```

Используется как шаблон обнаружения тестов по умолчанию, когда `--tests` не задан. Поддерживает `**` (рекурсивно). Форма списка объединяет совпадения.

**#75, молчаливые 0% при пустом обнаружении тестов.** `coverage --strict` больше не проваливается в `filepath.Walk(".")`, когда glob ничего не находит. Вместо этого он предупреждает:

Он предупреждает, что ни один тестовый файл не несёт аннотацию `@spec`/`@ac` и что поэтому
покрытие сообщит 0% для каждой спецификации, затем называет два средства: задать
`settings.tests_glob` в `specter.yaml` или передать `--tests <glob>`. Как и выше, дословный
текст не воспроизводится, потому что содержит длинное тире, которого этот документ
содержать не может.

При `strictness: zero-tolerance` предупреждение повышается до жёсткой ошибки. Сигнал доходит до оператора прежде, чем он потратит час на отладку «почему всё падает?».

## 7. Внедрение в Python (закрывает дешёвое исправление GH #79)

Экстрактор аннотаций из тела теста в `specter ingest` раньше принимал только `// @spec`. Пользователь pytest, написавший `print("# @spec my-spec")` внутри теста (естественная идиома Python), видел, что аннотация попадает в JUnit `<system-out>`, а затем отбрасывается ingest, потому что `#` не совпадал.

v0.11 расширяет регулярное выражение до `//`, `#` и `*` — те же три маркера, которые уже принимает сканер исходных файлов. Межъязыковой вывод соглашения B теперь проходит через ingest без языково-специфичных костылей.

```python
# tests/conftest.py: pytest pattern
import pytest

def pytest_configure(config):
    config.addinivalue_line("markers",
        "spec(spec_id, ac_id): bind a test to a Specter AC")

@pytest.fixture(autouse=True)
def _emit_spec_annotations(request):
    marker = request.node.get_closest_marker("spec")
    if marker:
        spec_id, ac_id = marker.args
        print(f"# @spec {spec_id}")
        print(f"# @ac {ac_id}")
```

Затем тест:

```python
@pytest.mark.spec("my-spec", "AC-01")
def test_thing(): ...
```

В `pytest.ini`:

```ini
[pytest]
junit_logging = system-out
junit_log_passing_tests = true
```

`pytest-specter` (плагин, формализующий этот шаблон) запланирован на следующий релиз. Расширение регулярного выражения разблокирует внедрение pytest уже сегодня.

## Миграция

Для большинства проектов v0.11 — замена без изменений. Три явных шага:

1. **Опционально: задайте `settings.strictness` и `settings.tests_glob` в `specter.yaml`.** Если не зададите, умолчания совпадут с поведением v0.10.x: `strictness: threshold`, `tests_glob` не задан (провал в обход по умолчанию).
2. **Опционально: установите хук pre-push.** `specter init --install-hook` из корня репозитория.
3. **Опционально: напишите файл инструкций для ИИ.** Выберите используемый инструмент и запустите `specter init --ai <tool>`.

Для проектов, задевших GH #75 или #76: опечатки в `specter.yaml` теперь дают ошибку, а не молча игнорируются. Если у вас сегодня есть неизвестный ключ, вы увидите ошибку при первом разборе на v0.11. Сообщение называет ближайший допустимый ключ.

Для пользователей Python: тесты pytest с комментариями `# @spec` теперь работают для `coverage`. Чтобы заработал `coverage --strict`, добавьте шаблон autouse-фикстуры в `conftest.py` выше (или подождите `pytest-specter`).

## Чего v0.11 не делает (и почему)

**Без языково-зависимого `specter explain`.** GH #77: `explain my-spec:AC-01` показывает пример на Go пользователям Python. Логика определения есть (по расширению), но не показывает настройку pytest. Запланировано; нужна проработка дизайна, сколько печатать.

**Без подсказки о диагностике «только исходники».** GH #80: когда `coverage --strict` находит аннотации в исходниках, но не находит соответствующей записи в `.specter-results.json`, он должен выдавать подсказку о требовании двух каналов. Запланировано.

**Без плагина `pytest-specter`.** Более правильное исправление GH #79. Дешёвое исправление (расширение регулярного выражения) разблокирует сегодня; плагин улучшит эргономику.

**Без поверхности VS Code для `settings.strictness`.** Боковая панель всё ещё показывает статус по порогу tier. Показ состояния строгости — кандидат на v0.12.

**Без обработки флейков.** Всё ещё отложено. Реальные паттерны из использования v0.10/v0.11 проинформируют дизайн.

## Более широкая картина

До v0.11 Specter мог сказать, что тест для AC-07 выполнился в CI и прошёл (вклад v0.10). Это необходимо, но недостаточно. v0.11 закрывает ещё три пробела:

- **Порядок операций механический.** Хук pre-push блокирует неаннотированные диффы локально; файл инструкций передаёт контекст спецификации ИИ до написания кода; `check --test` обеспечивает гигиену аннотаций тестов во время CI.
- **Поверхность конфигурации честна.** Опечатки дают ошибку. Неизвестные ключи дают ошибку. Пустое обнаружение тестов предупреждает. `strictness` явна.
- **Внедрение шире.** Естественная идиома Python проходит через ingest без костылей. Пять крупных ИИ-инструментов имеют путь в одну команду к файлу инструкций, знающему проект.

Цикл замыкается чуть дальше с каждым релизом:

- **v0.9.x**: существование теста механическое.
- **v0.10**: исход теста механический.
- **v0.11**: порядок операций механический, и конфигурация честна. Вы здесь.
- **v0.12**: эргономика Python, ИИ-хуки для жёсткого принуждения (PreToolUse / PostToolUse compact), поверхность строгости в VS Code.

v0.10 закрыл фазу оценки. v0.11 закрывает фазу порядка операций. Оставшиеся пробелы эргономические, а не структурные. На v0.12 остаётся сделать так, чтобы каждый язык и инструмент ощущались родными, а не перешагнуть ещё одну концептуальную дыру.
