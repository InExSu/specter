# Покрытие под контролем CI: закрываем дыру фазы eval

**Аудитория:** команды, уже использующие Specter, которые хотят, чтобы зелёный бейдж CI что-то значил.
**Что выпущено:** `specter ingest` + `specter coverage --strict` (v0.10).
**Что закрывает:** формы тихого прохода, где аннотированные, но падающие или пропущенные тесты считались «покрытыми».

---

## Зачем это существует

Миссия Specter — вести цикл **spec → test → implement → eval** в правильном порядке, каждый раз, с сохранением замысла на всём пути. До v0.9.x мы механически обеспечивали три из этих четырёх фаз:

- **Spec.** `parse`, `resolve`, `check` проверяют схему, связность и структуру.
- **Test (существование).** `coverage` считает аннотации `@spec`/`@ac` по AC и применяет пороги tier.
- **Implement.** Вне объёма по замыслу; Specter — шлюз, а не тренер IDE.
- **Eval.** Фактически не обеспечивался.

Последняя дыра была тихой. `specter coverage` считал AC «покрытым», когда находил аннотацию `// @ac AC-NN` на тесте. Он никогда не спрашивал, *прошёл* ли тест.

### Три формы тихого прохода

```go
// @ac AC-07
func TestHostMutexReleasedOnPanic(t *testing.T) {
    t.Skip("flaky, revisit")   // counted as covered
}

// @ac AC-08
func TestConcurrentRunSerializes(t *testing.T) {
    // was green last week, now panics
    // annotation still present → still counted as covered
}
```

Три способа, которыми это тихо ломается:

1. **Пропущенные тесты заявляют покрытие**: `t.Skip(...)` / `it.skip(...)` / `@pytest.mark.skip` сохраняют аннотацию, поэтому покрытие остаётся зелёным.
2. **Падающие тесты заявляют покрытие**: регрессии мержатся под зелёным шлюзом, потому что аннотация остаётся после поломки теста.
3. **Флейки портят сигнал**: тест, проходящий 70% времени, сообщает покрытие непоследовательно.

Проходящий конвейер Specter не означал, что ваш замысел проверен. Это ломало обещание.

## Дизайн (двухэтапный ingest)

Кратчайшим путём было бы `specter coverage --junit 'test-results/*.xml'` — научить `coverage` парсить JUnit inline. Мы отклонили это. JUnit XML — движущаяся цель между vitest, jest, go test, pytest, playwright, и каждый фреймворк пишет его немного по-своему. Связывать этот парсинг с горячим путём `coverage` сделало бы критическую стадию шлюза хрупкой.

Вместо этого v0.10 вводит два глагола с одним контрактом между ними:

```
test runner  →  specter ingest  →  .specter-results.json  →  specter coverage --strict
             (JUnit / go test -json)      (status enum)            (pass/fail gate)
```

Каждая стадия делает одно:

- **`specter ingest`** читает вывод раннера и пишет канонический файл результатов. Знает о причудах вариантов, чтобы `coverage` не пришлось.
- **`.specter-results.json`** — стабильный контракт. Поля не меняются без смены схемы.
- **`specter coverage --strict`** читает только файл результатов и выдаёт решение pass/fail. Быстро, детерминированно, независимо от раннера.

Это значит, что добавление нового варианта раннера (TAP, собственный JSON) — изменение только в `ingest`. `coverage` остаётся простым.

## Перечисление `status`

`.specter-results.json` в v0.9 имел булево поле `passed`. v0.10 добавляет явный статус:

```json
{
  "results": [
    { "spec_id": "engine-transaction", "ac_id": "AC-07", "status": "passed",  "passed": true },
    { "spec_id": "engine-transaction", "ac_id": "AC-08", "status": "failed",  "passed": false },
    { "spec_id": "engine-transaction", "ac_id": "AC-09", "status": "skipped", "passed": false },
    { "spec_id": "engine-transaction", "ac_id": "AC-10", "status": "errored", "passed": false }
  ]
}
```

Четыре значения:

| Статус | Значение |
|---|---|
| `passed` | Тест выполнился и его утверждения прошли. |
| `failed` | Утверждение не прошло. |
| `skipped` | Тест помечен skip / skip.if / xfail. |
| `errored` | Сам фреймворк упал вне утверждения: setup бросил исключение, teardown запаниковал, ошибка компиляции. Отличается от `failed`, потому что обычно указывает на инфраструктуру, а не на тестируемый код. |

Старый булев `passed` сохранён рядом с новым перечислением. Потребители на spec-coverage < 1.9.0 продолжают читать `passed` и видят ровно то, что видели раньше. Новые потребители читают `status` для более богатого сигнала. Без дня перехода.

### Худший статус побеждает

Когда одна и та же пара `(spec_id, ac_id)` задевается несколькими тестами — обычно когда у AC есть модульный и интеграционный тест, — испускаемая запись использует худший наблюдённый статус:

```
errored > failed > skipped > passed
```

Один падающий собрат понижает AC. Проходящий тест не лечит падающий. Это сохраняет семантику в соответствии с тем, как разработчики реально думают: «У AC-07 красный тест, значит AC-07 не покрыт, точка.»

## `coverage --strict` (принуждение)

Без флага покрытие сохраняет сегодняшнее поведение точно: только аннотации для Tier 2/3, с учётом pass-rate для Tier 1 при наличии файла результатов. Обновление до v0.10 ничего не меняет, пока вы не включите это.

С `--strict`:

- Каждый аннотированный AC должен иметь запись `status: passed` в `.specter-results.json`. Всё остальное — `failed`, `skipped`, `errored` или полное отсутствие (`unknown`) — понижает его до непокрытого.
- Понижение применяется ко **всем tier**, не только к Tier 1. Утилитарная спецификация Tier 3 с падающим аннотированным тестом непокрыта под `--strict`.
- Отсутствующий `.specter-results.json` — жёсткая ошибка. Пустой файл результатов предупреждает и понижает каждый аннотированный AC до непокрытого:
  ```
  error: --strict requires .specter-results.json — run 'specter ingest' first
  ```
  Молчаливый откат к только аннотациям под `--strict` уничтожил бы весь смысл, поэтому мы этого не делаем.

### Почему жёсткий отказ при отсутствии результатов

`--strict` — контракт: «Я проверил, что аннотированные тесты прошли.» Без файла результатов этот контракт нельзя выполнить. Трактовка отсутствующего файла как «ладно, поверим аннотациям» позволила бы командам выпустить сломанный конвейер и думать, что они защищены.

## Подключение CI, от начала до конца

Типичный проект на Node:

```yaml
name: CI
on: [pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx vitest run --reporter=junit > test-results/vitest.xml
      - uses: actions/upload-artifact@v4
        with: { name: test-results, path: test-results/ }

  specter-coverage:
    runs-on: ubuntu-latest
    needs: [test]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: { name: test-results, path: test-results/ }
      - run: specter ingest --junit 'test-results/vitest.xml' --output .specter-results.json
      - run: specter coverage --strict
```

Задача `specter-coverage` блокируется на `test`, потребляет его артефакт и шлюзует PR. Если любой аннотированный тест `failed`/`skipped`/`errored`, покрытие выходит с ненулевым кодом, и PR краснеет.

Цена: петля обратной связи теперь `max(длительность тестов) + ~30s`, где `~30s` — время прогона ingest + coverage на рабочих пространствах с несколькими сотнями спецификаций. Для проекта масштаба jwtms (250-секундный интеграционный набор) это маргинальная цена за гораздо более сильную гарантию.

### Можно ли запускать локально?

Да. В `--strict` нет ничего специфичного для CI. Единственное требование — раннер тестов, выдающий JUnit XML или `go test -json`, что является изменением одного флага в вашей существующей команде тестов:

```bash
$ go test -json ./... > /tmp/go.json
$ specter ingest --go-test /tmp/go.json
Wrote 34 result entries to .specter-results.json

$ specter coverage --strict
Spec Coverage Report — 15 specs · 99% avg coverage
  Tier 1: 4/4 passing (100%)
  Tier 2: 9/9 passing (100%)
  Tier 3: 2/2 passing (100%)
```

Подходит для pre-commit хуков, pre-push хуков или интерактивных проверок «я что-нибудь сломал?».

## Поэтапное внедрение v0.10

Дизайн допускает градуированное внедрение. Выберите строку, соответствующую вашему текущему состоянию:

1. **Нет тестов, нет CI** — `coverage` работает как раньше. `--strict` неприменим.
2. **Есть тесты, нет CI-раннера, выдающего структурированный вывод** — добавьте флаг `--reporter=junit` (или `-json` для go test). Всё. `ingest` + `--strict` теперь доступны.
3. **Есть JUnit / go-test-json в CI** — подключите две строки `run:` выше. Включите `--strict`, когда доверитесь сигналу.
4. **Уже используете `.specter-results.json` вручную** — для Tier 1 готово. Переходите на `--strict`, если хотите ту же гарантию для Tier 2/3.

Совместимость с булевым `passed` означает, что **принудительной миграции нет**. Старый инструментарий продолжает работать. Новый получает более богатый сигнал. Темп выбираете вы.

## Чего v0.10 не делает (и почему)

**Без обработки флейков.** Периодически падающий тест — реальная проблема, но предложение «добавить `--retry 2` в задачи тестов» — обход, скрывающий законные регрессии. Правильный ответ — раннеры испускают `status: flaky`, когда обнаруживают паттерн, а Specter обзаводится флагом `--deny-flaky`, трактующим `flaky` как отказ. Для этого нужны реальные паттерны из использования v0.10, прежде чем мы зафиксируем дизайн; отложено до v0.11.

**Без отслеживания исходных файлов.** `specter coverage --strict` по-прежнему работает с аннотациями в тестовых файлах. Открытый проектный вопрос, извлекать ли управление исходными файлами из аннотаций, не запланирован и отделён.

**Пока без поверхности VS Code.** Отображение состояния строгого режима в боковой панели (например, красная точка у AC, чей тест упал) — быстрое продолжение v0.10, не часть этого среза.

**`specter ingest` намеренно узок.** Он берёт вывод раннера и пишет канонический файл. Он не запускает тесты, не повторяет их, не анализирует длительности и не подсказывает, какие тесты писать. Каждое из этого — либо чужой инструмент, либо намеренная нецель.

## Более широкая картина

До v0.10 Specter мог сказать: «кто-то вспомнил написать тест для AC-07». После v0.10 Specter может сказать: «тест для AC-07 выполнился в CI и прошёл». Это гораздо более сильное обещание, и именно его на самом деле даёт заявление о миссии.

Цикл замыкается чуть дальше с каждым релизом:

- **v0.9.x.** Существование теста механическое.
- **v0.10.** Исход теста механический. Вы здесь.
- **v0.11.** Порядок операций механический (pre-push хук блокирует неаннотированные диффы; `explain --format claude --all` передаёт контекст спецификации ИИ до написания кода).

Каждая часть узкая и делает одно. Вместе они делают «разработку через спецификации» чем-то, что инструмент может проверить, а не чем-то, что команда обещает.
