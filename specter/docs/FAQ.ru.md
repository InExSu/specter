# Specter FAQ

Частые вопросы о Specter и разработке через спецификации.

---

## Что такое SDD?

Spec-Driven Development (SDD) — методология, в которой структурированные файлы спецификаций являются единственным источником истины (SSOT) для каждой функции системы. Спецификация определяет «что и почему» — контекст, цель, ограничения и критерии приёмки — до написания любого кода. Когда спецификация и код расходятся, права спецификация, а код неверен. SDD рассчитан на разработку с ИИ, где спецификации ограничивают пространство решений и дают проверяемый контракт для сгенерированного кода. Полную методологию см. в [материалах курса Mastering SDD](../../sddbook/INDEX.ru.md).

---

## Что такое микроспецификация?

Микроспецификация — фундаментальная единица спецификации в SDD. У каждой микроспецификации три столпа:

- **Контекст** — какую систему, функцию и зависимости описывает эта спецификация? Какие делаются допущения?
- **Цель** — что должен делать этот компонент? Что входит в объём, а что явно исключено?
- **Ограничения** — какие правила должны соблюдаться? У каждого ограничения есть ID (например, `C-01`), описание и уровень принуждения (`error`, `warning` или `info`).

Микроспецификация также включает **критерии приёмки** — проверяемые условия, доказывающие, что ограничения соблюдены. Каждый AC ссылается на ограничения, которые проверяет, создавая прослеживаемую связь от требования к проверке.

## Какие спецификации можно писать в Specter?

Specter не зависит от содержания. Всё, что укладывается в форму спецификации — контекст, цель, ограничения, критерии приёмки, — валидная спецификация. Конвейер (parse -> resolve -> check -> coverage -> sync) не проверяет, какую категорию контракта вы описываете.

Примеры, которые все живут в `.spec.yaml`:

- **Поведенческие контракты** — поведение во время выполнения эндпоинта, фоновой задачи, конечного автомата.
- **Инварианты данных** — «у каждого платежа есть tenant_id», «поля PII шифруются при хранении».
- **Безопасность и политика** — правила авторизации, аудит-логирование, ограничения соответствия.
- **Схемные и структурные контракты** — форма конфигурационного файла, payload вебхука, формат записи реестра.
- **Архитектурные правила** — «сервис A не должен напрямую вызывать сервис B».

Структура остаётся одинаковой в каждом случае: ограничения определяют правила, AC определяют, как их проверить, тесты дают механическое доказательство. Specter не нужно знать, является ли ограничение инвариантом времени выполнения или политикой — только что у него есть ID, описание и AC, который на него ссылается.

Практическое следствие: когда в вашем контракте есть *несущие данные* (список исключений, каталог разрешений, таблица feature-флагов), держите данные в sidecar-файле, а спецификации позвольте описывать формат, которому должны удовлетворять записи. Спецификация — определение типа; данные — каталог. Specter проверяет определение типа; ваш набор тестов или правило линтера проверяет каталог по нему.

## Почему YAML?

Specter использует YAML как формат спецификаций по нескольким причинам:

- **Читаемо для человека.** YAML легко читать и писать без инструментов. Разработчики могут создавать спецификации в любом текстовом редакторе.
- **Читаемо для ИИ.** Большие языковые модели надёжно разбирают YAML. Его можно включать прямо в промпты и контекстные окна.
- **Диффится.** YAML даёт чистые диффы в системе контроля версий, что упрощает ревью изменений спецификаций в pull request.
- **Существующая экосистема.** У YAML есть зрелые парсеры на каждом языке, поддержка валидации JSON Schema и широкая поддержка IDE с подсветкой синтаксиса и автодополнением.
- **Структурирован, но гибок.** YAML поддерживает вложенную типизированную структуру, нужную спецификациям (объекты, массивы, перечисления), без синтаксического шума JSON или неоднозначности Markdown.

## Чем Specter отличается от OpenAPI / Swagger?

OpenAPI описывает **поверхности API** — эндпоинты, схемы запросов/ответов, коды статусов. Он отвечает на вопрос «какую форму имеют данные?»

Specter описывает **контракты компонентов** — контекст, замысел, ограничения и критерии приёмки для любого компонента системы, не только API. Контракт может быть поведением времени выполнения, инвариантом данных, политикой безопасности, ограничением схемы или любым другим правилом, которому должен удовлетворять компонент. Он отвечает на вопрос «что этот компонент должен делать или гарантировать, почему и как мы это проверим?»

Ключевые различия:

- OpenAPI ограничен HTTP API. Спецификации Specter покрывают любую функцию: фоновые задачи, конечные автоматы, потоки аутентификации, конвейеры данных.
- OpenAPI не выражает ограничения вроде «НЕ ДОЛЖЕН превышать 200 мс времени ответа» или «ДОЛЖЕН повторить 3 раза перед отказом». Ограничения Specter — первоклассные.
- OpenAPI не моделирует зависимости между спецификациями. Specter строит граф зависимостей (`depends_on`) и находит циклические зависимости, несоответствия версий и структурные конфликты между спецификациями.
- Спецификации Specter включают критерии приёмки с явной прослеживаемостью к ограничениям. У OpenAPI эквивалента нет.

Эти два подхода дополняют друг друга. API-спецификация в Specter может ссылаться на схему OpenAPI для формата данных, добавляя сверху ограничения и критерии приёмки.

## Чем Specter отличается от Cucumber / BDD?

Cucumber и BDD-инструменты — **фреймворки исполнения тестов**. Они запускают сценарии, написанные на Gherkin, против живой системы, чтобы проверить поведение.

Specter — **инструмент проверки до реализации**. Он анализирует спецификации статически — до появления любого кода или тестов — чтобы поймать структурные проблемы: осиротевшие ограничения, циклические зависимости, отсутствующие критерии приёмки, ломающие изменения между версиями.

Ключевые различия:

- Cucumber требует работающей реализации. Specter работает только со спецификациями.
- Cucumber проверяет «соответствует ли код сценарию?» Specter проверяет «внутренне ли согласована спецификация и совместима ли она со своими зависимостями?»
- Сценарии Cucumber — проза. Спецификации Specter — структурированный YAML с типизированными полями, ID ограничений и явными объявлениями зависимостей.
- Инструмент покрытия Specter измеряет, *существуют* ли тесты для каждого критерия приёмки. Cucumber измеряет, *проходят* ли они.

Зрелый процесс SDD использует оба: Specter проверяет спецификации до реализации, а тестовые фреймворки (включая BDD-инструменты) проверяют реализацию после.

## Как внедрить Specter в существующую кодовую базу?

Начните с малого и двигайтесь наружу:

1. **Сгенерируйте черновики спецификаций из существующего кода.** Запустите `specter reverse src/ --output specs/`, чтобы извлечь черновики спецификаций из исходников TypeScript, Python или Go. Specter анализирует схемы валидации, утверждения тестов и сигнатуры функций, чтобы получить черновики `.spec.yaml`.
2. **Проверьте и завершите черновики.** Обратный компилятор извлекает структуру, но не замысел. Просмотрите каждую сгенерированную спецификацию, заполните AC, помеченные как пробелы, и добавьте недостающие ограничения.
3. **Аннотируйте существующие тесты.** Добавьте аннотации `@spec` и `@ac` к тестам, покрывающим описанное поведение. Запустите `specter coverage`, чтобы увидеть оставшиеся пробелы.
4. **Интегрируйте в CI.** Добавьте `specter sync` в ваш CI-конвейер. Он выходит с 0, только когда все обнаруженные спецификации достигают настроенных порогов.
5. **Расширяйтесь постепенно.** Добавляйте спецификации для новых функций по мере их создания. Со временем покрытие спецификациями растёт органически.

Используйте `specter doctor`, чтобы в любой момент проверить здоровье проекта. Он запускает все предварительные проверки и точно говорит, на что обратить внимание перед запуском полного конвейера.

## Что такое tier?

Tiers представляют уровень риска спецификации и определяют, насколько строго Specter применяет правила.

| Tier | Метка | Описание | Пример |
|------|-------|-------------|---------|
| 1 | Критический | Ключевая бизнес-логика, платёжные потоки, аутентификация, целостность данных. Отказы дороги или опасны. | `payment-create-intent`, `user-auth` |
| 2 | Стандартный | Важные функции с умеренным риском. Tier по умолчанию для большинства спецификаций. | `notification-send`, `report-generate` |
| 3 | Рекомендательный | Функции низкого риска, внутренние инструменты, экспериментальная работа. | `admin-dashboard-layout`, `dev-metrics` |

Tier влияет на принуждение по всему инструментарию:

- **`specter check`**: осиротевшие ограничения — ошибки в Tier 1, предупреждения в Tier 2 и info в Tier 3.
- **`specter coverage`**: Tier 1 требует 100% покрытия AC тестами. Tier 2 требует 80%. Tier 3 требует 50%.

Задайте tier в файле спецификации:

```yaml
spec:
  id: payment-create-intent
  version: "1.0.0"
  status: approved
  tier: 1
```

## Что такое ID ограничений и ID AC?

У каждого ограничения и критерия приёмки в спецификации есть уникальный идентификатор:

- **ID ограничений** следуют формату `C-01`, `C-02`, `C-03` и т.д.
- **ID AC** следуют формату `AC-01`, `AC-02`, `AC-03` и т.д.

Эти ID служат нескольким целям:

- **Прослеживаемость.** Каждый AC объявляет, какие ограничения проверяет, через `references_constraints`. Это создаёт проверяемую связь от требования к тесту.
- **Обнаружение сирот.** `specter check` отмечает любое ограничение, на которое не ссылается хотя бы один AC. Если ограничение существует, но ничто его не проверяет, это пробел.
- **Аннотация тестов.** Тестовые файлы ссылаются на ID AC аннотациями `// @ac AC-01`, чтобы `specter coverage` мог сопоставить тесты конкретным критериям приёмки.
- **Коммуникация.** В ревью кода и обсуждениях «C-03 не покрыт» точнее, чем «то ограничение про повторы».

Пример:

```yaml
constraints:
  - id: C-01
    description: "MUST validate email format before submission"
    type: technical
    enforcement: error

acceptance_criteria:
  - id: AC-01
    description: "Valid email is accepted"
    references_constraints: ["C-01"]
    priority: critical

  - id: AC-02
    description: "Invalid email returns a validation error"
    references_constraints: ["C-01"]
    priority: critical
```

Specter применяет формат ID при парсинге. `c1` или `ac-1` будут отклонены; правильные форматы — `C-01` и `AC-01`.

## Как интегрировать Specter с CI?

Используйте `specter sync` как CI-шлюз. Он запускает полный конвейер (parse → resolve → check → coverage) последовательно и выходит с ненулевым кодом при любом сбое:

```yaml
# GitHub Actions
- name: Validate specs
  run: specter sync
```

`specter sync` выходит с `0`, только когда:
- Все файлы спецификаций парсятся без ошибок схемы
- В графе зависимостей нет циклов и битых ссылок
- Нет ошибок фазы check; предупреждения валят только при `--strict` или `settings.strict: true`
- Все спецификации Tier 1 имеют 100% покрытия AC, все Tier 2 — 80%, все Tier 3 — 50%

Код выхода — `0` при успехе и `1` при сбое, поэтому он интегрируется с любой CI-системой, проверяющей коды выхода. Вы также можете запускать отдельные этапы конвейера (`specter parse`, `specter resolve`, `specter check`, `specter coverage`) для более тонкого контроля.

## Какие языки поддерживает Specter?

Формат `.spec.yaml` **не зависит от языка**. Спецификации описывают контракты компонентов — поведение времени выполнения, инварианты данных, схемы, политики, — а не детали реализации. Вы можете писать спецификации для систем, построенных на любом языке.

Инструментарий написан на Go и распространяется как единый бинарник без зависимостей времени выполнения.

Для покрытия тестами (`specter coverage`) сканирование аннотаций поддерживает:

- Комментарии `//` (JavaScript, TypeScript, Go, Rust, Java, C# и т.д.)
- Комментарии `#` (Python, Ruby, Shell, YAML и т.д.)

Обратный компилятор (`specter reverse`) поддерживает TypeScript, Python и Go. Он автоматически определяет язык по расширениям файлов, или вы можете указать его через `--adapter typescript|python|go`.

## Можно ли использовать Specter с Claude Code / Cursor / Copilot?

Да. Спецификации Specter предназначены для потребления ИИ-инструментами как часть их контекста.

**Claude Code:** добавьте пути к файлам спецификаций в ваш `CLAUDE.md`, чтобы Claude читал их до написания кода. Собственный `CLAUDE.md` Specter демонстрирует этот шаблон — он предписывает Claude читать соответствующую спецификацию до написания или изменения любого исходного файла.

**Cursor:** ссылайтесь на спецификации в файле `.cursorrules`. Например:

```
When working on the payment module, read specs/payment-create-intent.spec.yaml first.
All constraints in the spec are mandatory requirements.
```

**GitHub Copilot:** включите содержимое спецификации в промпт или откройте файл спецификации в соседней вкладке, чтобы он был доступен как контекст.

Ключевой принцип: спецификации — обычные YAML-файлы, помещающиеся в контекстные окна ИИ. Любой ИИ-инструмент, умеющий читать файлы, может их использовать. Структурированный формат (контекст, цель, ограничения, критерии приёмки) даёт ИИ именно ту информацию, которая нужна для генерации правильных реализаций и тестов.
