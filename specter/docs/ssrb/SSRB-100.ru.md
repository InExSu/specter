# SSRB-100: `spec.kind: audit-matrix` для сквозных спецификаций

Status: REJECT
Decided: 2026-04-26
Source: GH #100

## 1. Запрос

Добавить в схему спецификации дискриминатор `spec.kind` с начальным значением `audit-matrix` (по умолчанию сохраняется текущая форма). Спецификации аудиторской матрицы содержали бы строки путей/переходов/действий, каждая со `status: covered | gap | covered_needs_review` и `spec_ref`, указывающим на спецификацию, которой принадлежит поведение. Предназначено для выявления пробелов в сквозных вопросах (например, «отправляется ли квитанция на каждом пути завершения платежа?»).

## 2. Происхождение

В JWTMS было 5 спецификаций, явно являвшихся «матрицами покрытия»: каждая строка — путь (`PATH-N`), переход (`T-N`) или действие (`AUDIT-N`) со статусом + spec_ref. Их принудительно втискивали в `acceptance_criteria` (создавая дублирующиеся AC) или держали вне Specter (`specs.legacy/flows/`). Сквозной паттерн реален в регулируемых отраслях (HIPAA, SOC2, SOX, проверки безопасности, покрытие доступности).

## 3. Универсальность

Вердикт: UNCLEAR — *паттерн* универсален; *предложенная форма* специфична для JWTMS

Сквозные трекеры соответствия/аудита существуют в регулируемых отраслях. Потребность перечислять вопросы и отслеживать покрытие по ним подлинная. Но конкретная форма строк JWTMS (пути/переходы/действия со статусом + spec_ref) — один конкретный взгляд на более широкий паттерн. Другим доменам могут понадобиться иные формы строк. Полиморфный `spec.kind` — тяжеловесное обязательство поддерживать любую из них.

## 4. Цена принятия

- Каноническое определение схемы: существенно — каждое существующее обязательное поле становится «обязательным при kind=acceptance» или подобным; при `kind=audit-matrix` появляются новые обязательные поля.
- Модель типов в памяти: объединение или интерфейс с вариантами по kind.
- JSON-контракт: расширения редактора и CI-инструменты ветвятся по `kind` для каждой операции.
- Справочная документация: удваивается — каждому kind нужны собственные справочник, примеры, шаблоны инструкций для ИИ.
- Существующие пользовательские спецификации: изначально без издержек миграции; все по умолчанию `kind=acceptance`.
- Поверхности редактора: автодополнение, hover, боковая панель — всем нужна логика по kind. Поток создания спецификации спрашивает «какой kind?»
- Спецификации dogfooding: немедленного влияния нет; могут вырасти до использования audit-matrix.

Более глубокая цена — в будущем: каждая новая функция должна отвечать «к каким kind относится?» — взрыв схемы усугубляется таблицей функций × kind.

## 5. Существующее покрытие

Прямого механизма для сквозного представления сегодня нет. AC внутренни для спецификации; нет встроенного способа спросить «покажи все спецификации, затрагивающие `payment_completion`, и покрыто ли действие с квитанцией».

Но есть более лёгкие механизмы, приближающие сквозное представление без полиморфной схемы:

- `tags` + запросы (`specter ls --tag=audit-matrix-payment-receipt`) — уже частично поддерживается; нужен инструментарий на стороне запросов.
- Обратное связывание через будущее поле `governs:` у AC — любой AC может объявить `governs: [AUDIT-3]`, и Specter собирает сквозное представление из существующих критериев приёмки.
- Внешний файл трекера — JWTMS уже делает это через `specs.legacy/flows/`; приемлемый ответ для трекеров, не вписывающихся в форму AC.

## 6. Альтернативы

- **Обратное связывание через аннотацию `governs:`.** Любой AC может объявить `governs: [AUDIT-3]`. `specter ls --governs=AUDIT-3` собирает представление из существующих `acceptance_criteria`. Никакой новой формы спецификации, никакого раздвоения схемы. Дешёвое расширение существующей модели.
- **Теги + запросы.** `tags: [audit-matrix-payment-receipt]` + `specter ls --tag=audit-matrix-payment-receipt`. Уже поддерживается концептуально; недоинструментировано на стороне запросов.
- **Внешний файл трекера.** Сквозные матрицы живут в собственном формате (CSV, YAML, таблица Markdown) вне Specter. JWTMS уже так делает. Приемлемо для сквозных трекеров, не вписывающихся в форму AC и не требующих машинно-запрашиваемой интеграции.
- **Полиморфный `spec.kind`.** Предложенная форма. Самая тяжёлая. Откладывает все более лёгкие механизмы.

## 7. Решение

REJECT по форме решения, а не по обоснованности проблемы. Сквозной паттерн реален (§3), но полиморфный `spec.kind` — тяжеловесное обязательство по схеме (§4), тогда как более лёгкие механизмы (§6) покрывают сценарий гораздо дешевле. Сначала должны появиться обратное связывание через `governs:` или теги + запросы; если они окажутся недостаточными против боли реального второго проекта — вернуться к вопросу.

## 8. Триггеры пересмотра

- Второй несвязанный проект (регулируемая отрасль помимо JWTMS) сообщает о той же потребности И показывает, что обратное связывание / теги / внешние трекеры её не покрывают.
- Конкретный сквозной запрос оказывается неразрешимым без схемы по kind (например, проверка типов формы строки).
- Обратное связывание через `governs:` выходит, и adoption показывает, что это неверный примитив.
