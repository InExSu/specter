# SSRB-097: Плюральный массив `generated_from.source_files`

Status: REJECT
Decided: 2026-04-26
Source: GH #97

## 1. Запрос

Переименовать `generated_from.source_file` (единственная строка) в `generated_from.source_files` (плюральный массив строк), чтобы соответствовать существующей форме `generated_from.test_files`. Обратная совместимость: принимать `source_file` (единственное число) как сокращение для массива из одного элемента.

## 2. Происхождение

Миграция JWTMS на схему Specter v1.0.0 (~250 спецификаций). 46 из 249 спецификаций обоснованно перечисляли >1 исходного файла (максимум 19 — сквозные аудиторские/потоковые спецификации). Обходным путём было поместить первый путь в `source_file`, а остальные — в `spec.tags` с префиксом `src:`, злоупотребляя `tags` для данных в форме URI и разбивая один логический список на два поля.

## 3. Универсальность

Вердикт: SINGLE-PROJECT

Асимметрия единственного/множественного числа между `source_file` и `test_files` существует с v0.1. JWTMS — первый и единственный пользователь, отметивший это. Сообщённое трение специфично для миграции (вручную отредактированное содержимое спецификаций, импортированное из другого диалекта схемы). Ни один другой проект Specter не сообщал о той же боли за месяцы после v0.1.

## 4. Цена принятия

- Каноническое определение схемы: переименование + смена типа (строка → массив); добавление псевдонима обратной совместимости.
- Модель типов в памяти: `SourceFile string` → `SourceFiles []string` (или оба, с устареванием).
- JSON-контракт: нижестоящие потребители (расширение VS Code, сторонние инструменты) проверяют новую форму.
- Справочная документация: переименование по всему `docs/`.
- Шаблоны инструкций для ИИ: любые фрагменты схемы упоминают новое поле.
- Существующие пользовательские спецификации: правило канонизации `doctor --fix` для переименования.
- Поверхности редактора: минимально — сегодня ни один UI не завязан на это поле.
- Спецификации dogfooding: минимально — собственные спецификации Specter написаны вручную, а не получены обратной компиляцией.

## 5. Существующее покрытие

Каноническая схема сейчас не выражает происхождение из нескольких файлов. Обходной путь через `tags` реально используется; правильный ответ — не искривлять `tags`, но из этого не следует, что схему нужно менять.

## 6. Альтернативы

- **Обходной путь с ручным редактированием `tags`.** Статус-кво. Функционально, но непрозрачно; `tags` не предназначен для URI.
- **Транслятор форм `specter migrate --from=jwtms` (GH #96).** Когда появится инструмент миграции, он при импорте поглотит более плоскую форму `spec.source_files` из JWTMS, не ослабляя каноническую схему. Асимметрия остаётся; стоимость поглощает инструмент миграции.
- **Расширение `specter reverse`.** Если сам `reverse` создаёт черновики, где вывод из нескольких исходных файлов — естественная форма, это отдельное проектное решение, но оно не всплывало.
- **Обобщить `generated_from` до `provenance`.** Открытая тема проектирования; более крупный редизайн, не подходящий объём для этого запроса.

## 7. Решение

REJECT согласно §3 и §6. Асимметрия единственного/множественного числа — реальная проблема формы (цена §4 нетривиальна, но решаема), однако единственное документированное пользовательское трение — у JWTMS, а сценарий миграции имеет не-схемное решение в адаптере `specter migrate --from=<dialect>` из GH #96. «Соответствовать существующей форме `test_files`» — аргумент симметрии, а не пользовательского трения; он не проходит планку универсальности.

## 8. Триггеры пересмотра

- Второй несвязанный проект независимо сообщает о том же трении в не-миграционном использовании.
- `specter reverse` создаёт черновики, где вывод из нескольких исходных файлов — естественная форма, а единственное число вынуждает к потерям.
- Будущий пользователь обнаруживает боль, которую не может поглотить инструмент миграции из GH #96.
