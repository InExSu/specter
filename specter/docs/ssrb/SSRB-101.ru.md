# SSRB-101: Управление исходными файлами, аннотация (F7) против списка `governs:` (F8)

Status: REJECT (закрыт как not-planned)
Decided: 2026-08-16, раньше целевого окна
Source: BACKLOG «Не запланировано, сначала нужна проектная работа» (отслеживание исходных файлов на основе аннотаций; обобщить `generated_from` до `provenance` со списком `governs:`)

## 1. Запрос

Два конкурирующих предложения отвечают на один вопрос: *«как Specter
узнаёт, какие исходные файлы управляются спецификацией?»*:

- **F7, на основе аннотаций.** Распространить аннотации `// @spec <id>` с
  тестовых файлов на исходные. Новая команда `specter specs governing <path>`.
  Вывод покрытия несёт производный массив `source_files: [...]` для каждой
  спецификации. Включается настройкой в `specter.yaml`. Без изменения схемы
  `.spec.yaml`.

- **F8, декларативный список `governs:`.** Обобщить `generated_from`
  до `provenance` с полем `governs: [string]`, перечисляющим управляемые
  исходные файлы для каждой спецификации. У исходных файлов нет аннотаций. Новое
  поле схемы.

Эти два — взаимоисключающие варианты по умолчанию. Проекты не должны нести
оба механизма, отвечающих на один вопрос.

## 2. Происхождение

Миграция JWTMS вскрыла базовую потребность: спецификация управляет конкретными
файлами реализации, а у Specter сегодня нет первоклассного способа
записать это отображение (только `generated_from.test_files` для тестов).
Обратный компилятор создаёт черновики, где связь с исходными файлами
неявна.

Боль реальна (один проект попросил); предложенная форма — два
разных дизайна, которые нужно оценить, а не одно зафиксированное изменение.

## 3. Универсальность

**UNCLEAR** в начале оценки (2026-05-07). Один проект (JWTMS)
попросил. Окно оценки (v0.13–v0.16, примерно 4–6 месяцев) предназначено,
чтобы выявить или не выявить второй несвязанный запрос.

Решение «да, выпускаем один из них» требует доказательств как минимум от
2 независимых проектов согласно планке универсальности проекта.

## 4. Цена принятия

### F7 (на основе аннотаций)

| Поверхность | Влияние |
|---|---|
| Каноническая схема | Нет |
| Модель типов в памяти | Новое производное поле в отчёте покрытия |
| JSON-контракт | Новый массив `source_files: [...]` в выводе покрытия (поверхность контракта v1.0) |
| Справочные документы | Новый шаблон аннотаций задокументирован; зеркалит аннотацию тестов |
| Пользовательские спецификации (миграция) | Нет |
| Поверхности редактора | Новый hover/переход к спецификации для исходных файлов |
| Dogfood | Specter должен аннотировать собственные `internal/**/*.go` |
| Производительность | `coverage` сканирует каждый исходный файл, подходящий под настройку-эквивалент `tests_glob`; большие репозитории платят за каждый прогон |
| Режимы дрейфа | Принципиально новые: spec-id в аннотации, которого не существует; спецификация переименована без обновления аннотации |

### F8 (список `governs:`)

| Поверхность | Влияние |
|---|---|
| Каноническая схема | Новое поле у каждой спецификации (или под существующим `generated_from` / новым объектом `provenance`) |
| Модель типов в памяти | Новое обязательное-или-необязательное поле |
| JSON-контракт | Следствие смены схемы; `parse --json` несёт новое поле |
| Справочные документы | Новое поле схемы задокументировано в `SPEC_SCHEMA_REFERENCE.md` |
| Пользовательские спецификации (миграция) | Существующим спецификациям нужно добавить списки `governs:`, если они хотят принуждения управления (или миграционный инструмент заполняет его) |
| Поверхности редактора | Hover по `governs:` показывает отображение спецификация-файл |
| Dogfood | Specter должен перечислить исходные файлы в 15+ спецификациях; бремя поддержки |
| Производительность | Без сканирования; объявленный список потребляется напрямую |
| Режимы дрейфа | Высокие: список устаревает при перемещении/переименовании/удалении файлов; новый класс отказов для миграций |

F8 несёт обязательство по схеме до 1.0; F7 — нет. У F7 есть стоимость
производительности на больших репозиториях; у F8 — стоимость дрейфа на каждом репозитории.

## 5. Существующее покрытие

Сегодня ни одного механизма нет. `generated_from` (единственный
`source_file`, необязательный) записывает *как* спецификация была создана (часто через
`specter reverse`), а не *чем она управляет*. SSRB-097 уже отклонил
путь «сделать `generated_from.source_files` плюральным» по основаниям
универсальности + симметрии-против-трения.

## 6. Альтернативы

### Гибрид

Отображение `governs:` на уровне манифеста (в `specter.yaml`, а не в каждой
`.spec.yaml`). Централизует отображение; без изменения схемы спецификаций;
без аннотаций в исходниках. Сочетает отсутствие изменения схемы из F7 с
декларативной формой F8.

Компромисс: манифест становится горячей точкой поддержки; теряется свойство F7
«истина живёт рядом с кодом».

### Обратное связывание через `depends_on`

Существующий `depends_on` мог бы нести ссылки на исходные файлы, если его
обобщить. Компромисс: смешивает зависимость спецификация-спецификация с управлением
спецификация-файл; SSRB-097 фактически отклонил это направление.

### Только соглашение об именовании файлов

`payment-charge.spec.yaml` и `internal/payment/charge.go` связаны
именем; явного отображения нет. Компромисс: работает для проектов с нуля, не работает для
легаси, требует определённой раскладки репозитория.

### Задокументированный шаблон адаптера (без схемы, без команды)

Потребители конкретного проекта подключают собственный контроль управления через
существующий вывод `parse --json` и соглашения проекта. Компромисс:
без первоклассной поддержки; каждый пользователь заново изобретает колесо.

## 7. Решение

NEEDS-DESIGN. Открыто в v0.13–v0.16. Критерии решения:

- Если за окно оценки 0 дополнительных проектов запросят управление
  И существующие альтернативы-соглашения/адаптеры покрывают
  сценарий → закрыть как not-planned (F7 и F8 отклонены).
- Если 1+ дополнительных проектов запросят это И запрос можно обслужить
  путём F7 без изменения схемы → ACCEPT F7, выпуск в v0.17 или v0.18.
- Если 1+ дополнительных проектов запросят это И F7 в одиночку не справляется (например,
  сгенерированный/vendored код, который нельзя аннотировать) → рассмотреть гибрид
  (манифестный `governs:`) раньше поля схемы `governs:` из F8.
- Планка поля `governs:` на уровне спецификации у F8 самая высокая: требуется доказательство,
  что ни F7, ни гибрид не достаточны.

## 8. Триггеры пересмотра

- Второй несвязанный проект (после JWTMS) сообщает о боли управления
  исходными файлами, которая соответствует любому из предложений.
- `unreachable_annotation` из v0.13 (F3) выходит и выявляет паттерны,
  информирующие любой из дизайнов.
- Бенчмарки производительности на большом репозитории (50K+ исходных файлов) меняют

- Участник v0.17/v0.18 предлагает гибридный вариант на уровне манифеста
  с достаточным дизайном.

## 10. Закрытие, 2026-08-16

**И F7, и F8 отклонены. Закрыто как not-planned до окончания окна
оценки.**

Будьте точны в причине, потому что очевидное прочтение неверно. Это закрылось не
потому, что время вышло. Окно шло с v0.13 по v0.16, а проект
находится на v0.14.1, так что оно закрывается досрочно, на основании находки, а не
на отсутствии запросов.

### Находка

Оценка потока оркестрации от 2026-08-16 изучила workflow, который
выглядел нуждающимся именно в этом. Его шлюз запрета заглушек описывается как статическое сканирование
каждой функции, привязанной к критерию приёмки, что предполагает
отображение спецификация-исходник. Это выглядело как второй заявитель, которого ждал этот бриф.

Это не так, и причина обобщается за пределы того workflow. **Оркестратор,
замораживающий дерево между фазами, уже точно знает управляемый набор
файлов** — из диффа с замороженной ссылкой. Это реальное происхождение,
записанное актом заморозки. Оба кандидата здесь — приближения
происхождения, которым вызывающий в такой позиции уже владеет, и оба несут дрейф,
которого нет у диффа: аннотация может назвать несуществующую спецификацию или
остаться после переименования, а объявленный список устаревает при каждом перемещении файла.

Так что самый правдоподобный будущий заявитель управления исходными файлами оказывается
лучше обслужен без него. Это более сильная причина закрыть, чем молчание, и
она не зависит от ожидания.

### Раздел 3 независимо поддерживает тот же вывод

Универсальность была записана как UNCLEAR с одним просящим проектом. Их осталось один.
Workflow выше не повышает её по двум независимым основаниям: он происходит
из самого проекта, а не от пользователя, и триггер раздела 8 просит
именно второй **несвязанный** проект. Считать внутренний бриф
означало бы считать один голос дважды — именно этот отказ и призвана предотвращать планка
универсальности.

Отдельная точка данных от пользователя режет так же. OpenWatch рассматривал
управление на основе аннотаций для собственного использования и отказался, используя рассуждение
самого Specter: аннотация у функции реализации не имеет видимого раннеру
аналога, поэтому она может быть только непроверяемым утверждением. Это
обдуманный отказ, и его не следует записывать как спрос.

### Что это не решает

Проблема реальна и остаётся нерешённой. Здесь не сказано, что проекту никогда не
нужно знать, какими файлами управляет спецификация. Сказано, что ни один кандидат в этом
брифе не является способом это узнать, и что вызывающему, замораживающему дерево, это не нужно.

### Триггеры переоткрытия, заменяющие раздел 8

- Второй проект, несвязанный с исходным заявителем и не сам проект Specter,
  сообщает о боли управления исходными файлами и называет блокируемый workflow.
- Потребность в гранулярности **на уровне функций**, а не файлов, то есть
  какая функция реализует названный критерий, а не какие файлы затронула фаза. Дифф
  замороженной ссылки обслуживает второе и не может обслужить первое. Ничто в текущей
  работе над оркестрацией этого не требует.
- Workflow, который не может замораживаться, то есть фазы, идущие в общем дереве без
  ссылки контроля версий, что убирает происхождение, на которое опирается это закрытие.

  Python-плагином в соответствии с согласованием дорожной карты от 2026-08-16.
- Слот запасного варианта F7/F8 в v0.18 пустеет.
- Две записи backlog вытесняются: отслеживание исходных файлов на основе аннотаций и
  обобщение `generated_from` до `provenance` со списком `governs:`. Обе
  отмечены в проходе груминга 2026-08-16.
